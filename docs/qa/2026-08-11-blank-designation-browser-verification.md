## 통과한 항목 (실제 브라우저 조작 결과)

### 1. 등록 → 지정 → 저장

본문 `예산의 3요소는 편성, 집행, 결산 이다.` 입력 후 지정 모드 전환. 어절 버튼이 `[예산의, 3요소는, 편성, 집행, 결산, 이다]`로 렌더되고 **구두점은 클릭 대상에서 제외**됐다(설계대로).

`편성` 클릭 → textarea `예산의 3요소는 {{b1}}, 집행, 결산 이다.`
`집행` 클릭 → textarea `예산의 3요소는 {{b1}}, {{b2}}, 결산 이다.`

아래 빈칸 후보 목록이 `b1/편성`, `b2/집행`으로 자동 채워졌고 **빈 자리표시자 행은 남지 않았다** — Task 4 리뷰의 Critical(G1) 수정이 실제 화면에서 동작함을 확인.

저장 성공. DB 확인:

```
id  |                  content
254 | 예산의 3요소는 {{b1}}, {{b2}}, 결산 이다.
blank_key | answer_text
b1        | 편성
b2        | 집행
```

### 2. 조사 분리와 경계 조정

본문 `배관을 통하여` → `배관을` 클릭:

| 조작 | 정답 | 본문 |

계획서 표와 정확히 일치한다.

### 3. 해제 왕복

X 버튼 클릭 → 본문이 `배관을 통하여`로 **원형 그대로** 복원되고 빈칸 목록이 비었으며 어절이 다시 클릭 가능해졌다.

### 4. 수정 화면

문제 254의 수정 화면에서 지정 모드로 전환하니 기존 `{{b1}}`·`{{b2}}`가 **추가 코드 없이 파싱만으로** 빈칸 칩으로 표시됐다. `결산`을 추가 지정하니 서버에서 불러온 키와 충돌 없이 `b3`가 발번됐고, 저장 후 DB에 `b1/편성 · b2/집행 · b3/결산`으로 반영됐다.

## 발견된 결함

### B1 (Critical) — 같은 키의 마커가 두 번 나오면 고아 마커가 그대로 저장된다

`releaseBlank`·`adjustBlankBoundary`가 `content.indexOf(marker)`로 **첫 번째 출현만** 찾는다. 두 번째 칩을 조작해도 첫 번째가 바뀐다.

재현 (실제 조작):

1. 본문 `수도는 {{b1}}이고 다시 {{b1}}이며 항구는 {{b2}}이다`, 빈칸 `b1/서울`·`b2/부산`을 수동 목록으로 입력
2. 지정 모드 전환 → 칩 3개(서울·서울·부산)
3. **두 번째** `서울` 칩의 X 클릭
4. 결과: 본문 `수도는 서울이고 다시 {{b1}}이며 항구는 {{b2}}이다`, 빈칸 목록은 `b2/부산`만 남음

이제 본문에 **어떤 빈칸도 선언하지 않은 `{{b1}}` 리터럴**이 남는다. `validateBlanks`는 선언된 키가 본문에 있는지만 검사하고 그 반대는 보지 않으므로 클라이언트·서버 양쪽을 통과한다. 실제로 저장됐다:

```
id  |                      content                      | status
255 | 수도는 서울이고 다시 {{b1}}이며 항구는 {{b2}}이다  | ARCHIVED
blank_key | answer_text
b2        | 부산
```

**학습자 화면에 `{{b1}}`이 날것으로 노출된다.** 경고도 오류도 없다.

> 재현용으로 만든 255번은 학습자에게 노출되지 않도록 화면에서 **보관 처리**해 두었다.

### B2 (Critical) — 중복 키 칩이 React key를 중복시킨다

같은 상황에서 브라우저 콘솔에 실제로 찍혔다:

```
Encountered two children with the same key, `blank-b1`. Keys should be unique so that
components maintain their identity across updates. Non-unique keys may cause children
to be duplicated and/or omitted
```

`BlankDesignator`가 blank 세그먼트의 key를 `blank-${seg.key}`로 잡는데, 같은 키의 마커가 두 번 나오면 형제 노드 두 개가 같은 key를 갖는다. 계획의 완료 기준 "브라우저 콘솔에 React 오류 없음"에 걸린다.

### B3 (Important) — 기존 `{{blank_1}}` 데이터를 클릭하면 편집본이 깨진다

`blankSegments.js`의 `MARKER`가 `/\{\{(b\d+)\}\}/g`라 **`b`+숫자 형식만** 마커로 인식한다. 그런데 이 앱 자신의 빈칸 키 입력란 placeholder가 `blank_1`이고, DB의 기존 문항도 그 형식을 쓴다.

재현 (문제 229, 실제 조작):

1. 본문 `대한민국의 수도는 {{blank_1}}이고, 최대 항구도시는 {{blank_2}}이다.`
2. 지정 모드 전환 → 마커가 칩이 아니라 **평범한 클릭 가능 어절** `{{blank_1}}이고`로 렌더된다(이미 빈칸이라는 표시가 전혀 없다)
3. 클릭 → 본문 `대한민국의 수도는 {{b1}}, 최대 항구도시는 {{blank_2}}이다.`, 빈칸 목록에 `b1` / 정답 `{{blank_1}}이고` 추가

마커 문자열 자체가 정답 텍스트가 되고 원래 `blank_1`은 고아가 된다. 저장은 `본문에 없는 빈칸 마커입니다: blank_1`로 막히지만(다행), **관리자가 편집 중이던 내용은 되돌릴 수단 없이 깨진다.**

## 권고

B1·B2는 같은 뿌리(같은 키의 마커가 여러 번 나오는 상태를 아무도 막지 않는다)에서 나온다. B3는 마커 문법이 두 가지로 갈라져 있다는 별개 문제다. 셋 다 **정상 경로가 아니라 기존 데이터·수동 입력과 만나는 지점**에서만 나타나므로, 앞선 단위 테스트와 코드 리뷰가 전부 통과한 채로 남아 있었다.

## 수정과 재검증 (커밋 `0e3430a`)

### 설계 판단

**같은 키의 마커가 여러 번 나오는 것을 금지하지 않기로 했다.** 서버 `validateBlanks`가 금지하지 않고 기존 데이터에도 존재할 수 있으므로, 막을 것이 아니라 다뤄야 한다. 한 키는 정답이 하나라는 사실에서 두 규칙이 따라 나온다.

- **해제는 그 키의 모든 출현을 함께 되돌린다.** 하나만 되돌리면 반드시 고아가 생긴다(그것이 B1이었다).
- **경계 조정(±1)은 출현이 2개 이상이면 성립하지 않는다.** 정답은 공유되는데 각 마커 뒤 글자가 다르다(`{{b1}}이고` vs `{{b1}}이며`). 그래서 막고, 버튼을 비활성화하며 이유를 title로 알린다 — 눌러도 아무 일이 없으면 고장으로 보이기 때문이다.

`MARKER` 정규식은 `/\{\{(b\d+)\}\}/g` → `/\{\{([A-Za-z0-9_-]+)\}\}/g`로 넓혀 키 형식에 종속되지 않게 했다. blank 세그먼트에는 word와 같은 의미의 `start`/`end` 오프셋을 부여해 React key를 위치 기반(`blank-${start}`)으로 바꿨다.

### 재검증 결과 — 결함을 처음 잡아낸 그 브라우저에서 그대로

| | 수정 전 (실측) | 수정 후 (실측) |
|---|---|---|
| **B1** 두 번째 칩 해제 | `수도는 서울이고 다시 {{b1}}이며 …` — 고아 마커 잔존, 그대로 저장됨 | `수도는 서울이고 다시 서울이며 항구는 {{b2}}이다` — **고아 없음** |
| **B2** 콘솔 | `Encountered two children with the same key, blank-b1` | **오류 0건** |
| **B3** 문제 229 지정 모드 | `{{blank_1}}이고`가 클릭 가능한 어절로 렌더 | `blank_1`·`blank_2`가 **정답이 담긴 칩**으로 렌더, 마커 문자열이 어절로 새지 않음 |

중복 키 `b1`의 ◀▶ 버튼은 `disabled` 상태이고 title에 "b1 마커가 본문에 여러 번 있어 정답 범위를 조정할 수 없습니다"가 붙는다. 중복이 아닌 `b2`의 버튼은 정상 활성이다.

마커 유사물 `{b1}`·`{{ b1 }}`·`{{}}`는 정규식을 넓힌 뒤에도 여전히 마커로 인식되지 않는다(각각 blank 세그먼트 0개).

프론트엔드 **221개 전부 통과**(기존 216 + 신규 5), 빌드 성공.

### 데이터 정리

- 재현용으로 만든 255번(고아 마커 포함)은 학습자에게 노출되지 않도록 **보관 처리**했다.
- 254번은 정상 문항이라 활성으로 남겼다.
- **문제 229는 수정 작업 중 다른 내용으로 두 번 저장됐다가**(감사 로그 81·82) 원래 상태 `대한민국의 수도는 {{blank_1}}이고, 최대 항구도시는 {{blank_2}}이다.` + `blank_1/서울`·`blank_2/부산`으로 **화면에서 복원했다**(DB 확인 완료).

### 남은 제약

`validateBlanks`는 여전히 "선언된 키가 본문에 있는가"만 검사하고 그 반대(본문의 모든 마커가 선언돼 있는가)는 보지 않는다. 지정 모드가 고아 마커를 만드는 경로는 위 수정으로 닫혔지만, **본문을 직접 손으로 고치거나 빈칸 후보 목록에서 행을 삭제하면 여전히 고아 마커를 만들 수 있다**(이 브랜치 이전부터 있던 동작). 이 검사를 추가하려면 클라이언트만 고칠지 서버까지 고칠지 판단이 필요해 이번 범위에서 제외했다.
