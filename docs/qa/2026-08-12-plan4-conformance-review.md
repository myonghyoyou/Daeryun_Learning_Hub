## 1. 백엔드 — 실행으로 검증한 것

### 1.1 채점 규칙 (PRD 6.3)

계획: *단일선택/OX는 단일 정답 일치, 다중선택은 정답 집합 완전 일치, 주관식은 정규화(trim/대소문자무시/공백정리) 후 일치, 빈칸은 노출된 빈칸을 모두 맞혀야 정답*

실제 API 호출 결과:

| 유형 | 입력 | 결과 |
|---|---|---|
| MCQ_SINGLE | 정답만 | ✅ 정답 |
| | 오답 | 오답 |
| | 정답+오답 함께 | **오답** |
| MCQ_MULTI | 정답 집합 완전 일치 | ✅ 정답 |
| | 정답 일부만 | **오답**(부분 점수 없음) |
| | 정답 전부 + 오답 하나 | **오답** |
| | 빈 선택 | 오답 |
| OX | 정답 / 오답 | ✅ 정확 |
| SHORT_ANSWER | `Not Found` | ✅ 정답 |
| | `not found` | ✅ 정답(대소문자 무시) |
| | `  Not   Found  ` | ✅ 정답(공백 정규화) |
| | `찾을 수 없음` | ✅ 정답(복수 정답 중 하나) |
| | `NotFound` | 오답 — **공백 압축이지 제거가 아니다** |

전 항목이 계획과 일치한다.

### 1.2 빈칸 제출 검증 (Approved Amendments)

계획: *제출 목록을 `Set<String>`으로 만들어 원소 수가 제출 수와 같은지 확인 → `definedKeys.containsAll(submittedKeys)` → `submittedKeys.size() == blankRevealCount` 순서로 검증. 실패 시 채점/저장하지 않는다.*

| 입력 | 결과 |
|---|---|
| 정상 1건 | ✅ 채점됨 |
| 개수 초과(2건) | 거부 `resultCode 1000` |
| 미정의 키 `b9` | 거부 |
| 중복 키 `b1` 2회 | 거부 |
| 빈 제출 | 거부 |

코드도 계획이 지정한 **순서 그대로**다(`SolveServiceImpl`).

### 1.3 정답 비노출

문제 상세(`GET /api/problems/{id}`) 응답을 유형별로 원문 검사:

| 유형 | 정답 필드 노출 |
|---|---|
| MCQ_SINGLE / MCQ_MULTI / OX | ❌ 없음 ✅ |
| SHORT_ANSWER | ❌ 없음 ✅ |
| FILL_BLANK | **의도적 노출** — 아래 참조 |

FILL_BLANK만 `answerText`가 응답에 있는데, 이는 계획이 요구한 것이다(*"선택되지 않은 빈칸은 정답 텍스트를 그대로 보여준다"*). **문제는 "풀어야 할 빈칸의 정답이 새는가"인데, 4회 조회 모두 겹침 0이었다:**

```
풀 빈칸=b2  정답노출된키=b1,b3  겹침=0
풀 빈칸=b1  정답노출된키=b2,b3  겹침=0
풀 빈칸=b3  정답노출된키=b1,b2  겹침=0
풀 빈칸=b3  정답노출된키=b1,b2  겹침=0
```

객관식은 `ChoiceOption(id, text)`라는 **정답 필드가 아예 없는 자료형**을 쓴다 — 실수로 샐 여지가 구조적으로 막혀 있다.

### 1.4 빈칸 무작위 노출

6회 연속 조회: `b2, b3, b1, b3, b1, b3` — 매 조회마다 다시 뽑힌다(`SecureRandom`). 계획대로다.

### 1.5 DB 계약

- `is_correct` 컬럼 매핑: `AttemptMapper.xml`이 `a.is_correct AS correct`로 별칭 처리. 주석에 이유까지 기록돼 있다
- `submitted_answer VARCHAR(500)` 절단: `SolveServiceImpl`에 500자 초과 시 자르는 코드와 주석 존재
- 새 마이그레이션 없음 ✅

### 1.6 태그 필터

`lower(ft.name) = lower(#{tag})`로 대소문자 무관 일치 — 계획의 "Task 계약 보완"대로다.

## 2. 프론트엔드 — 로직은 맞고 디자인 계약이 빈다

### 2.1 지켜진 것

| 요구 | 상태 |
|---|---|
| 목록에 결과 없음·로딩·오류 상태 | ✅ `EmptyState` / "불러오는 중..." / "다시 시도" |
| 이력을 PC 테이블 · 모바일 카드로 | ✅ `DataTable` + `md:hidden` 카드 |
| 정답·오답을 색상과 텍스트로 함께 | ✅ |
| 제출 전 정답 비노출, 제출 후에만 표시 | ✅ |
| 제출 중 중복 클릭 방지 | ✅ `Button loading={submitting}` |
| 날 Tailwind → 디자인 토큰 재표현 | ✅ `bg-blue-600`·`bg-gray-50` 등 **잔재 0건** |
| `SolveHomePage`의 로그아웃 보존 | ✅ `SolveShell`이 고정 |
| 선택지 터치 크기 | ✅ `px-4 py-3` (약 46px) |
| 마커 정규식 통일 `[A-Za-z0-9_-]+` | ✅ 서버·지정 모드·풀이 렌더 3곳 일치 |

### 2.2 미구현 — 학습 홈 구조 (가장 큰 차이)

계획서 Task 4 Step 6과 디자인 시스템 §8.2가 요구하는 학습 홈:

```
1행: ContinueLearning 8열 + ProgressPanel 4열
2행: RecommendedProblemSet 8열 + RecentActivity 4열
3행: RoutinePanel 12열
순서: 이어서 학습하기 → 학습 현황 → 추천 문제 → 최근 활동 → 학습 루틴
```

**실제 구현: 카드 3개(랜덤으로 풀기 / 골라서 풀기 / 내 풀이 이력)뿐이다.**

코드에서 다음 식별자를 검색한 결과 **0건**: `ContinueLearning`, `ProgressPanel`, `RecommendedProblemSet`, `RecentActivity`, `RoutinePanel`, "학습 현황", "최근 활동", "학습 루틴".

즉 **5개 영역 중 "문제 풀기" 진입 하나만 구현됐고 나머지 4개(학습 현황·추천 문제 세트·최근 활동·학습 루틴)는 없다.**

> **다만 이것이 전부 Plan 4의 책임인지는 따져야 한다.** `ProgressPanel`(학습 현황)과 `RecentActivity`(최근 활동)는 **집계 데이터가 있어야 만들 수 있고, 그 집계가 Plan 5(통계)의 목표다.** 계획서 스스로 "다음 Plan: Plan 5 — 이 Plan에서 쌓이는 `attempts` 데이터를 집계"라고 적고 있다. 반면 `RecommendedProblemSet`과 `RoutinePanel`은 Plan 5 의존이 아니다.

### 2.3 미구현 — 모바일 하단 고정 제출 영역

계획서 Design Contract: *"모바일은 1열 카드·**하단 고정 제출 영역**·터치 가능한 선택지 크기를 사용한다."*

풀이 화면 전체에서 `sticky`·`fixed bottom`·`bottom-0` 검색 결과 **0건**. 제출 버튼이 문서 흐름 안에 있어, 보기가 많은 문제에서는 모바일에서 스크롤해야 제출 버튼에 닿는다.

1열 카드와 터치 크기는 지켜졌다.

### 2.4 부분 미구현 — `/solve/:id`의 위계

계획서: *"`/solve/:id`는 **문제 번호·진행률·유형**·본문·제출 영역의 위계를 유지한다."*

| 요소 | 상태 |
|---|---|
| 문제 번호 | ❌ 없음 |
| 진행률 | ❌ 없음(랜덤 세트 진행 화면에만 `1 / 5`) |
| 유형 표시 | ❌ 없음 — `problem.type`은 렌더 분기에만 쓰이고 화면에 배지가 없다 |
| 본문·제출 영역 | ✅ |

목록 화면에는 유형 배지가 있는데(`TYPE_LABELS`), **상세로 들어가면 사라진다.**

> 단건 풀이에 "진행률"은 원래 성립하지 않는 개념이다(목록에서 하나 고른 것이므로). 계획서의 이 문장은 세트 풀이를 상정한 흔적으로 보인다. **문제 번호와 유형 배지는 단건에서도 유효한 요구다.**

### 2.5 약한 부분 — 선택지 포커스 표시

선택지 `<label>`에 `focus-visible` 스타일이 없다. 내부 `<input type="radio">`가 네이티브 포커스 링을 받긴 하지만, 다른 요소들이 전부 `focus-visible:outline-[3px] outline-brand-aqua`로 통일된 것과 달리 여기만 브라우저 기본이다.

계획서의 접근성 기준(*"포커스 링 유지"*)에 비추면 미달로 볼 여지가 있다.

## 4. 계획에 없었으나 추가된 것

Plan 4 이후 두 브랜치에서 다음이 들어갔다. **계획 위반이 아니라 사용자 피드백에 따른 확장이다.**

- 랜덤 풀이(문제 수·부서 지정 → 세트 → 결과 요약)
- 학습 홈 3갈래 분리
- 돌아가기 수단
- 빈칸 마커 표시용 함수(목록·이력·결과)

이 중 **랜덤 세트 진행 화면에는 진행률(`1 / 5`)이 있어**, 계획서가 `/solve/:id`에 요구했던 진행률이 다른 화면에서 실현된 셈이다.

# 부록: 디자인 시스템 준수 검토 (2026-08-12 추가)

`docs/superpowers/specs/2026-07-29-blue-bento-design-system.md`의 §8.3~8.5, §9.2를 실제 코드와 수치 단위로 대조했다.

## 요약

**토큰 정의는 명세와 완전히 일치한다.** `tokens.css`의 타입 스케일 8종이 §4.2 표와 px 단위까지 같고, 날 Tailwind 유틸 사용도 0건이다.

**그러나 화면 명세는 상당 부분 어긋난다.** 토큰을 "쓰긴 썼는데" 명세가 지정한 수치·구조를 따르지 않은 경우가 많다.

## A. 명시적 위반 — 명세가 하지 말라고 한 것

### A1. 목록 항목을 별도 카드로 만들었다

§8.4.1: *"문제 항목은 하나의 Surface 안에서 row separator로 구분한다. **각 항목을 별도 카드로 만들지 않는다.**"*

실제: `<ul className="space-y-2">` 안에서 항목마다 `<Surface as={Link}>` — **정확히 금지된 형태**다.

### A2. 콘텐츠 최대 폭이 다르다

§8.4.1: 최대 콘텐츠 폭 **1120px**, 좌우 padding 28px
실제: `SolveShell`이 `max-w-[1040px]`, `px-5 md:px-7`(20/28px)

폭만 80px 좁다.

## B. 수치 미달 — 접근성·터치와 직결된다

| 항목 | 명세 | 실제 | 차이 |
|---|---|---|---|
| 보기 최소 높이 | **56px** (§8.4) | `px-4 py-3` + 22px 행간 = **46px** | −10px |
| 보기 간 세로 간격 | **10~12px** (§8.4) | `space-y-2` = **8px** | −2~4px |
| 주관식 입력 높이 | **44px** (§8.4.2) | `h-[38px]` | −6px |

> ⚠️ **명세 자체의 모순:** §7.5는 Input 기본 높이를 **38px**(모바일 40px)로 규정하는데 §8.4.2는 주관식을 **44px**로 요구한다. 두 조항이 충돌한다. 풀이 화면은 터치 입력이 주 사용처이므로 화면별 조항(§8.4.2)을 따르는 것이 맞다고 판단하나, **명세를 고쳐 충돌을 없애야 한다.**

## E. 판단이 필요한 것

**C1의 "진행률"은 단건 풀이(`/solve/:id`)에 성립하지 않는다.** 목록에서 하나를 고른 화면이므로 "몇 번째"가 없다. 명세와 Plan 4가 세트 풀이를 상정하고 쓴 문장으로 보이며, **랜덤 세트 진행 화면에는 이미 `1 / 5`가 있다.** 단건에는 문제 유형만 넣는 것이 맞다.

**§8.4.2의 12-column 레이아웃**(본문 8열 + 학습 진행·문제 정보 4열)도 마찬가지다. 4열에 넣을 "학습 진행"이 단건에는 없고 "문제 정보"는 유형·태그 정도다. 현재의 단일 컬럼이 실제 정보량에 맞는다 — **명세를 코드에 맞춰 고치는 편이 낫다.**
