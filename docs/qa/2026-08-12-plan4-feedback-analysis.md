## 1. 랜덤 풀이 — 문제 수와 부서를 정해서 풀기

### 1.1 지금 무엇이 없나

현재 풀이는 **목록에서 하나 골라 → 풀고 → 목록으로 돌아오는** 단발 구조뿐이다. "10문제 뽑아서 연달아 푼다"는 개념이 코드 어디에도 없다.

확인한 사실:

| 확인 대상 | 현재 상태 |
|---|---|
| `GET /api/problems` | 조건에 맞는 **전부**를 반환. 개수 제한도 무작위도 없음 |
| `ProblemSolveListItem` | `id`, `type`, `content`, `tags` — **부서 필드가 없다** |
| 목록 SQL `findAllActive` | `WHERE p.status='ACTIVE'` + 키워드/태그 조건뿐. **부서 조건 없음** |
| 부서 목록 API | `/api/admin/departments`가 **`@RequireRole(SUPER_ADMIN)`** |
| `attempts` 테이블 | 제출 1건 = 1행. **세트·회차 개념 없음** |

### 1.2 가장 큰 걸림돌 — 직원은 부서 목록을 가져올 수 없다

"부서를 정해서 푼다"면 화면에 부서 선택 드롭다운이 필요하다. 그런데 부서 목록을 주는 API가 **총괄관리자 전용**이다. 부서관리자조차 호출하면 403이고(Plan 3 QA에서 이미 확인된 사항), 직원은 당연히 안 된다.

즉 **부서 필터는 백엔드 API 추가 없이는 화면을 만들 수 없다.**

선택지:

| 안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| A | `GET /api/departments` 신설 (로그인 사용자면 조회 가능, 활성 부서만) | 태그 API(`/api/tags`)가 이미 같은 방식이라 일관됨 | 엔드포인트 하나 늘어남 |
| B | 기존 `/api/admin/departments`의 role 제한 완화 | 새 코드 없음 | 관리자 전용 경로에 직원이 들어옴. 응답에 비활성 부서·내부 정보 포함 |
| C | 풀이 목록 응답에 부서를 실어 보내고 화면에서 뽑아 씀 | API 추가 없음 | 문제가 0건인 부서는 선택지에 안 나옴. 목록 전체를 받아야 함 |

**권고: A.** `/api/tags`가 이미 "로그인만 하면 누구나 조회"라는 선례를 만들어 뒀고, 그 컨트롤러 주석에 근거까지 적혀 있다. 같은 패턴을 따르는 게 가장 자연스럽다. 활성 부서만 내려주면 정보 노출도 최소다.

### 1.3 무작위 추출을 어디서 하나

| 안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| 서버 | `GET /api/problems/random?count=10&departmentId=3` → 무작위 N건 | 문제가 많아져도 전송량 일정. `ORDER BY random() LIMIT n` 한 줄 | 엔드포인트 추가 |
| 화면 | 목록 전부 받아서 화면에서 섞고 앞 N개 | 백엔드 무변경 | 문제가 수천 건이면 전부 내려받음. 이미 목록에 페이지네이션이 없어 문제가 누적됨 |

**권고: 서버.** 지금은 활성 문제가 10건뿐이라 화면 방식도 돌아가지만, 문제 은행은 계속 커지는 게 전제다. 나중에 목록에 페이지네이션이 붙으면 화면 방식은 바로 깨진다.

빈칸 문제의 노출 빈칸을 서버가 `SecureRandom`으로 뽑는 선례(`SolveServiceImpl.selectRandomBlankKeys`)도 이미 있다.

### 1.4 반드시 먼저 정해야 할 것 4가지

구현 전에 답이 없으면 만들 수 없다.

**① 뽑은 문제 목록을 어디에 보관하나**

10문제를 뽑아 1번을 풀었다. 2번으로 넘어갈 때 나머지 9개를 어떻게 기억하나?

- 화면 상태에만 둔다 → 새로고침하면 세트가 통째로 날아간다. 구현은 가장 간단
- 브라우저 저장소(sessionStorage) → 새로고침을 견딘다. 다른 기기에서는 이어서 못 함
- 서버에 세트를 저장 → 어디서든 이어서 가능. **테이블 신설이 필요하고 규모가 크게 늘어난다**

**권고: sessionStorage.** 새로고침으로 세트가 사라지는 건 사용자가 겪으면 바로 불만이 되는데, 서버 저장은 이 피드백이 요구하는 범위를 넘는다.

**② 중간에 나가면 어떻게 되나**

5문제 풀고 나갔다가 돌아오면 이어서 푸나, 새로 시작하나? 이어서 푼다면 ①의 답과 맞물린다.

**권고: 이어서 풀기 제안 없이 새로 시작.** 다만 이미 제출한 5건은 이력에 그대로 남는다(현재 구조가 그렇다).

**③ 다 풀면 무엇을 보여주나**

- 아무것도 없이 목록으로 → 성취감이 없다
- **결과 요약(10문제 중 7개 정답)** → 자연스럽지만 화면 하나가 더 필요
- 통계 화면으로 연결 → Plan 5 영역이라 지금은 불가

**권고: 간단한 결과 요약 화면.** 세트 풀이의 마무리로는 이게 최소선이다.

**④ 이미 푼 문제를 또 뽑아도 되나**

반복 학습이 목적이면 상관없다. "안 푼 것 위주"로 하려면 `attempts`와 조인해 제외해야 하고 쿼리가 복잡해진다.

**권고: 일단 중복 허용.** 현재 구조가 같은 문제 재제출을 이미 허용하고 있고(덮어쓰지 않고 이력이 쌓인다), 반복 학습과도 맞는다. "안 푼 것만" 옵션은 나중에 덧붙일 수 있다.

### 1.5 부서 필터가 정책과 충돌하는지 확인 필요

계획서에 **"문제는 어느 부서가 등록했든 전사 직원이 공통으로 풀 수 있다"**고 명시돼 있다. 그래서 지금 목록에 부서 조건이 없는 것이다.

이번 요청의 "부서 정해서 풀기"는 **접근 제한이 아니라 사용자가 스스로 고르는 필터**로 이해된다. 즉 영업팀 직원이 개발팀 문제를 못 푸는 게 아니라, 원하면 개발팀 문제만 골라 풀 수 있게 하는 것이다.

**이 해석이 맞는지 확인이 필요하다.** 만약 "자기 부서 문제만 풀 수 있게" 하려는 의도라면 계획서의 전사 공통 원칙을 뒤집는 것이므로 별도 결정 사항이다.

## 2. 골라서 풀기 — 기능은 있고 입구가 없다

피드백에도 "이미 있는 방식이긴 함"이라고 적혀 있다. 실제로 `/solve/problems`에서 검색·태그 필터로 골라 푸는 기능이 동작한다.

**진짜 문제는 학습 홈이다.** 지금 홈에는 카드가 두 개뿐이다.

```
[문제 풀기]        → 목록으로
[내 풀이 이력]     → 이력으로
```

"문제 풀기"라는 이름이 **모든 풀이 방식을 대표하는 것처럼 보인다.** 여기에 랜덤이 추가되면 이름만으로는 둘을 구분할 수 없다.

**권고:** 홈을 세 갈래로 바꾸고 이름을 역할에 맞게 고친다.

```
[랜덤으로 풀기]    → 문제 수·부서 고르고 세트 시작
[골라서 풀기]      → 기존 목록 (검색·태그)
[내 풀이 이력]     → 그대로
```

디자인 시스템 §8.2에 **"추천 문제 세트는 icon/제목/설명/태그/주 행동 순서"**라는 규격이 이미 있다. 랜덤 카드는 이 규격을 그대로 쓰면 된다 — 새로 디자인할 필요가 없다.

**결정 필요:** 카드 3개를 나란히 둘지, 랜덤을 주 행동으로 크게 두고 나머지를 작게 둘지. 디자인 시스템은 "첫 번째 Primary Action"을 강조하는 구조를 권하고 있다.

## 3. 빈칸 입력칸을 가운데부터 입력되게

### 원인

`ProblemSolvePage.jsx`의 빈칸 입력칸에 정렬 지정이 없어 브라우저 기본값(왼쪽)이 적용된다.

```
mx-1 inline-block w-28 rounded-sm border-0 border-b-2 border-brand-blue
bg-surface-blue px-1 py-0.5 ...
```

밑줄만 있는 빈칸 모양인데 글자가 왼쪽에 치우쳐 있어 어색하다는 지적이다.

### 해결

`text-center` 한 클래스면 된다. **가장 단순한 항목이다.**

### 함께 볼 것

폭이 `w-28`로 고정돼 있다. 정답이 길면 넘치고, 짧으면 빈 공간이 크다. 가운데 정렬을 하면 **짧은 답일 때 빈 공간이 양옆으로 갈라져 더 눈에 띈다.**

| 안 | 내용 |
|---|---|
| 고정 폭 유지 | 지금 그대로. 문장 줄바꿈이 안정적 |
| 정답 길이에 맞춰 폭 조정 | 자연스럽지만 **정답 글자 수가 노출된다** — 힌트가 된다 |
| 입력 길이에 따라 늘어남 | 타이핑 중 문장이 출렁인다 |

**권고: 고정 폭 유지 + 가운데 정렬만.** 정답 길이 노출은 채점의 공정성을 해친다.

## 4-a. 태그 선택지가 이상하다

### 실제 데이터

DB를 직접 조회했다.

| 태그 | 활성 문제 수 |
|---|---|
| 엑셀 | 4 |
| 개발 | 2 |
| 지리 | 1 |
| 태그 | 1 |
| 네트워크 | 1 |
| 수정태그 | 1 |
| **과학** | **0** |
| **기초** | **0** |

원인이 **두 가지가 겹쳐 있다.**

### 원인 ① 설계 — 쓰이지 않는 태그까지 전부 보여준다

화면은 `listTags()`로 **지금까지 만들어진 모든 태그**를 가져온다. 반면 문제 목록은 **활성 문제만** 보여준다.

그래서 `과학`·`기초`를 고르면 **반드시 "조건에 맞는 문제가 없습니다"가 뜬다.** 고를 수는 있는데 결과가 절대 안 나오는 선택지다.

이건 데이터를 정리해도 재발한다. 문제를 보관 처리하는 순간 그 태그가 다시 유령이 되기 때문이다. **구조를 고쳐야 한다.**

### 원인 ② 데이터 — QA 잔여물

`태그`, `수정태그`, `엑셀`은 이전 QA에서 만든 흔적이다. 특히 `태그`·`수정태그`는 이름 자체가 의미 없다. 실무 태그(`지리`, `네트워크`)와 섞여 있어 더 어수선해 보인다.

### 해결 선택지

| 안 | 내용 | 평가 |
|---|---|---|
| A | 활성 문제에 실제로 붙어 있는 태그만 내려주는 API 신설 | **근본 해결.** 보관 처리에도 자동 대응 |
| B | 목록 응답의 태그를 화면에서 모아 선택지 구성 | API 추가 없음. 필터 전 목록을 한 번 받아야 하고, 필터된 상태에서 갱신하면 선택지가 줄어드는 이상 동작 |
| C | 태그 데이터만 정리 | 증상만 사라짐. **재발한다** |

**권고: A + C.** 구조를 고치고(A), QA 잔여 태그도 함께 정리한다(C). A만 하면 `태그`·`수정태그`가 활성 문제에 붙어 있어 여전히 선택지에 남는다.

**결정 필요:** 관리자 화면의 태그 필터도 같은 문제를 갖는지 확인하고 함께 고칠지. 관리자는 보관 문제도 다루므로 전체 태그가 맞을 수 있다 — 즉 **두 화면이 서로 다른 태그 목록을 써야 할 수 있다.**

## 4-b. Select 화살표가 오른쪽에 너무 붙어 있다

### 원인

`Select.jsx`가 브라우저 기본 `<select>`를 그대로 쓴다.

```
h-[38px] w-full rounded-sm border bg-surface-default px-3 text-body ...
```

`px-3`(12px)은 **글자에만** 적용된다. 화살표는 브라우저가 오른쪽 테두리에 딱 붙여 그린다. 게다가 모양과 위치가 브라우저마다 다르다.

디자인 시스템 §7.5는 좌우 패딩 12px만 규정하고 화살표는 언급이 없다. 즉 **명세 공백이지 명세 위반은 아니다.**

### 해결

`appearance-none`으로 기본 화살표를 끄고, 아이콘을 직접 배치한 뒤 오른쪽 패딩을 늘린다. 위치를 우리가 통제하게 되고 브라우저 차이도 사라진다.

### 영향 범위 주의

`Select.jsx`는 **공용 컴포넌트**다. 관리자 화면 곳곳(부서·계정·문제 필터, 유형 선택 등)이 함께 바뀐다.

- 이득: 전 화면 일관성
- 위험: 회귀 범위가 넓고, 자동 검증이 안 되는 영역이다(jsdom 없음)

**권고: 공용 컴포넌트를 고친다.** 풀이 화면에서만 다르게 보이면 그게 더 어색하다. 다만 **바뀌는 화면을 전부 눈으로 확인**해야 한다.

| D1 | 부서 필터가 "사용자 선택"인가 "접근 제한"인가 | **사용자 선택** — 전사 공통 원칙 유지 |
| D2 | 부서 목록을 어떻게 줄 것인가 | **신규 API 신설** |
| D3 | 무작위 추출을 어디서 하나 | **서버** |
| D4 | 뽑은 세트를 어디에 보관하나 | **sessionStorage** |
| D5 | 세트를 다 풀면 무엇을 보여주나 | **결과 요약 화면** |
| D6 | 이미 푼 문제를 또 뽑아도 되나 | **허용** |
| D7 | 학습 홈 카드 구성 | **3갈래**(랜덤/골라서/이력) |
| D8 | 태그 선택지를 어떻게 좁히나 | **활성 문제 기준 API + 데이터 정리** |
| D9 | 관리자 화면 태그 필터도 함께 고치나 | **당장 함께 고치지 않는다** |
| D10 | `Select` 공용 컴포넌트를 고치나 | **고친다** |

D1 확정에 따라 **부서는 접근 제한이 아니라 사용자가 스스로 고르는 필터**다. 영업팀 직원이 개발팀 문제를 못 푸는 것이 아니라, 원하면 개발팀 문제만 골라 풀 수 있게 하는 것이다. 계획서의 전사 공통 원칙은 그대로 유지된다.

D9 확정에 따라 관리자 화면의 태그 필터는 **기존 `/api/tags`(전체 태그)를 그대로 쓴다.** 새로 만드는 활성 태그 API는 직원 풀이 화면에서만 쓴다.

## 작업 순서 제안

**1단계 — 즉시 (반나절)**
3번(빈칸 중앙 정렬), 4-b(Select 화살표), 4-a 데이터 정리. 서로 독립적이고 결정 사항이 없다.

**2단계 — 구조 (1~2일)**
4-a 태그 API, D2 부서 API. 1단계와 무관하게 진행 가능하고 3단계의 선행 조건이다.

**3단계 — 랜덤 풀이 (3~5일)**
D1·D3~D7이 정해진 뒤 착수. 백엔드 추출 API → 설정 화면 → 세트 진행 → 결과 요약 순.

**검증:** 3단계는 화면 비중이 커서 단위 테스트로 덮이지 않는다(jsdom 부재). **브라우저 검증을 반드시 포함**해야 한다 — 이번 빈칸 기능에서 모든 자동 검증을 통과한 Critical 결함 2건이 브라우저에서만 잡힌 전례가 있다.
