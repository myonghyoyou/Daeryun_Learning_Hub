## 2. 찾은 결함과 조치

### D1 — 채점 결과 Surface 가 항상 흰색 (Critical)

명세는 정답 Success / 오답 Danger 배경을 요구한다. 실측 결과 정답 화면 배경이 `rgb(255,255,255)` — 그냥 흰색이었다.

`Surface` 가 `bg-surface-default` 를 고정으로 붙이고 `ProblemSolveCard` 가 뒤에 `bg-success-bg` 를 덧붙이는 구조였다. **클래스 문자열의 순서는 아무 영향이 없다** — 스타일시트에 나중에 생성된 클래스가 이긴다. 빌드 산출물 기준:

```
.bg-danger-bg       -> 14006
.bg-success-bg      -> 14284
.bg-surface-default -> 14520   ← 가장 뒤라 항상 이김
```

**조치**: `Surface` 에 `background` prop 추가(기본값 `bg-surface-default`). 톤을 바꿀 때는 className 이 아니라 이 prop 을 쓴다. 우선순위 다툼도 `!important` 도 없다.

실측 재확인:

| 상태 | 배경 | 제목 색 |
|---|---|---|
| 정답 | `rgb(240, 252, 246)` = `--color-success-bg` | `rgb(8, 124, 89)` |
| 오답 | `rgb(255, 240, 242)` = `--color-danger-bg` | `rgb(201, 65, 85)` |

두 Surface 는 radius 10px · padding 20px · border 1px `#E3EAF2` · 제목 17px/24px w700 로 **구조가 동일하고 색만 다르다** (Step 3 비교쌍 통과).

### D2 — 로딩 skeleton 이 "문제 목록" 링크를 빠뜨려 카드가 36px 튐 (Important)

`ProblemSolvePage` 의 로딩 분기가 `<ProblemSkeleton />` 만 그리고, 로드가 끝난 뒤에야 상단의 "문제 목록" 뒤로가기 링크가 생겼다. 그 링크(높이 20px + `mb-4` 16px)가 나중에 끼어들면서 **카드 전체가 36px 아래로 밀렸다** — skeleton 이 막으려던 바로 그 현상이다. 로딩 중에는 목록으로 돌아갈 방법도 없었다.

랜덤 세트 진행 화면(`RandomPlayPage`)은 같은 상황에서 진행률 헤더를 skeleton 상태에도 그리고 있었다. 단건 풀이 화면만 어긋나 있었다.

**조치**: 링크를 조건 분기 밖으로 올려 두 상태가 같은 자리에 그리게 했다.

실측 (1440×1024, 문제 233 — 보기 3개로 skeleton 과 개수 동일):

| 지표 | 수정 전 skeleton → 로드 | 수정 후 skeleton → 로드 |
|---|---|---|
| 카드 top | 108 → 144 (**+36**) | 144 → 144 (**0**) |
| 보기 목록 top | 242 → 251 (+9) | 278 → 251 (−27) |
| 제출 영역 top | 458 → 467 (+9) | 494 → 467 (−27) |

카드 위치 흔들림은 사라졌다. 남은 27px 은 **본문 줄 수 차이**다 — skeleton 은 본문을 2줄로 가정하는데(20px×2 + 8px) 문제 233 의 본문은 1줄이다. 문제마다 본문 길이가 달라 완전히 없앨 수 없는 종류의 차이이며, 본문이 2줄인 문제에서는 거의 0 이 된다.

### D3 — 접기 토글이 펼침 상태를 노출하지 않음 (Minor)

`Collapsible` 의 "더 보기"/"접기" 버튼에 `aria-expanded` 가 없었다. 눈에 보이는 문구는 바뀌므로 치명적이지는 않지만 disclosure 위젯의 표준 속성이다.

**조치**: `useId()` 로 본문에 id 를 주고 버튼에 `aria-expanded` + `aria-controls` 추가. 실측 확인 — 접힘 `aria-expanded="false"`, 펼침 `"true"`, `aria-controls` 대상 요소 존재.

### D4 — 제출 안내 자리 2px 어긋남 (Minor, 보류 항목이었음)

skeleton 의 안내 문구 자리가 `h-5`(20px)인데 실제 안내 문구는 `text-body-small` 한 줄 = **18px** 이었다. 구현자가 토큰을 읽지 않고 추정한 값이라 보류돼 있던 항목이다.

**조치**: `h-4.5` 로 교체. 빌드 산출물에서 `.h-4\.5{height:calc(var(--spacing) * 4.5)}` 생성 확인 (4px × 4.5 = 18px).

## 6. Step 4 — 키보드 (1440×1024)

### Tab 순서

| 화면 | 순서 |
|---|---|
| 학습 홈 | 문제 은행 Hub → 로그아웃 → 랜덤으로 풀기 → 골라서 풀기 → 내 풀이 이력 → 세트 시작하기 |
| 문제 목록 | (헤더 3개) → 학습 홈 → 내 풀이 이력 → 검색 입력 → 태그 select → 검색 버튼 → 목록 첫 행 |

**모든 포커스 지점에서 `outline: 3px solid rgb(0, 180, 227)`(= `--color-focus` / brand-aqua)** 확인. 목록 행만 offset −3px(안쪽), 나머지는 +2px.

- 보기 선택지: `label` 의 `focus-within` 링이 `3px solid rgb(0,180,227)` offset 2px ✅
- 목록 행 **Enter** → `/solve/problems` → `/solve/485` 이동 ✅
- 목록 행 **Space** → 이동하지 않음. `<a>` 의 기본 동작상 불가하며 §8.4.1 이 요구하나 **고치지 않고 기록만 한다**(role/keydown 처리가 필요해 이 브랜치 범위를 넘음)
- 제출 버튼은 답안 미입력 시 `disabled` 라 Tab 이 건너뛴다. 보기를 Space 로 고르면 곧바로 Tab 대상이 된다 ✅

> **측정 주의**: 이 화면들은 `transition-colors` 를 쓰기 때문에 포커스 직후 `getComputedStyle` 을 읽으면 전이 중간값이 나온다. 실제로 `rgb(255,255,255)`(currentColor) → `rgb(13,167,210)` → `rgb(0,180,227)` 로 수렴하는 것을 관측했다. **포커스 이동 후 최소 500ms 는 기다린 뒤 읽어야 한다.** 이 대기 없이 읽으면 "포커스 링 색이 틀렸다"는 잘못된 결론이 나온다.

## 9. 이번 QA 로 새로 알게 된 것 (수정하지 않음)

### 이력의 "제출 답안"이 객관식에서 `[104]` 로 표시된다

객관식 문제를 풀면 이력 화면 "제출 답안" 칸에 선택지 텍스트가 아니라 **선택지 ID 배열**이 그대로 나온다.

원인은 백엔드다 — `SolveServiceImpl` 이 제출 시점에 `submittedIds.toString()` 을 요약 문자열로 저장한다. 화면은 저장된 값을 그대로 보여줄 뿐이다.

**이 브랜치에서 고치지 않았다.** 백엔드 무변경이 이 브랜치의 전제이고, 이미 저장된 기존 이력 행의 형식까지 함께 다뤄야 하는 문제라 별도 작업으로 분리하는 것이 맞다. 실사용자에게 보이는 문구 문제이므로 **다음 작업 후보로 올린다.**

### 문제 보기는 2~5개로 제한된다

QA 데이터를 만들다 확인했다 — 보기 8개로 만들려 하자 `resultCode 1000`, "보기는 2개 이상 5개 이하이어야 합니다."

### `/favicon.ico` 가 404 다

콘솔에 404 가 찍히는 유일한 원인. 기능 영향 없음.

## 11. 측정 방법 메모 (다음 사람에게)

1. **`transition-colors` 가 걸린 요소는 포커스 직후 읽지 마라.** 최소 500ms 대기. 이 함정으로 "포커스 링이 흰색"이라는 잘못된 결론에 두 번 도달했다가 재측정으로 뒤집었다.
2. **라우트 지연 주입은 한 번만 쓰고 즉시 `unroute` 하라.** 반복하면 `ERR_INSUFFICIENT_RESOURCES` 로 브라우저 연결이 끊긴다(이전 세션 중단 원인). 이번에는 문제 233 하나에 대해 두 번만 쓰고 매번 `unroute` 했다.
3. **CSS 클래스를 새로 쓰면 빌드 산출물(`frontend/dist/assets/*.css`)에서 생성 여부를 확인하라.** 이 브랜치에서 "코드는 그럴듯한데 CSS 가 안 나오거나 다른 값으로 폴백되는" 실패가 이번 D1 을 포함해 다섯 번 나왔고 전부 이 방법으로만 잡혔다.
4. **`page.fill` / `page.click` 이 멈추면** 대상 탭이 다른 페이지일 수 있다. `page.evaluate` 로 `location.href` 를 먼저 확인하라.
