## 0. 시작 전 필독 — 환경 준비

### 0.1 현재 DB는 사실상 비어 있다

2026-08-07 기준 Docker DB(`localhost:5434`) 상태:

| 테이블 | 건수 |
|---|---|
| `users` | 1 (`admin` / SUPER_ADMIN / HQ) |
| `departments` | 1 (`HQ` 본사, ACTIVE) |
| `problems` · `tags` · `audit_logs` · `excel_upload_logs` | **0** |

**Plan 1·2 체크리스트 §0.3.1에 적힌 QA 계정(`admin2`, `deptadmin`, `emp002`, `legacy01`)과 부서(`DEV`, `SALES`, `OLD`)는 이 DB에 존재하지 않는다.** 그때와 다른 DB 상태다. 아래 §0.4대로 새로 만들어야 한다.

`admin` 비밀번호는 2026-08-07에 초기화했다.

| 사번 | 비밀번호 | 비고 |
|---|---|---|
| `admin` | `changeme1234` | **최초 로그인 시 변경 강제** (`must_change_password = true`) |

### 0.2 SMTP가 없으면 부서 격리 QA를 아예 할 수 없다

**이 문서에서 가장 중요한 검증은 §2 부서 격리이고, 그러려면 DEPT_ADMIN 계정이 반드시 필요하다.** 그런데 Plan 2의 `UserAdminServiceImpl.create`는 `insert → mail → audit`를 한 트랜잭션으로 묶으므로 **메일 발송이 실패하면 계정 생성이 통째로 롤백된다**(의도된 설계). 임시 비밀번호는 화면·응답·로그 어디에도 평문으로 나오지 않으므로 **메일을 실제로 열어 볼 수단이 없으면 만든 계정에 로그인할 수 없다.**

MailHog를 띄우고 시작한다.

```bash
docker run -d --name mailhog -p 1025:1025 -p 8025:8025 mailhog/mailhog
```

백엔드 기동 시 아래를 지정하고, 받은 메일은 `http://localhost:8025`에서 확인한다.

```
MAIL_HOST=localhost
MAIL_PORT=1025
MAIL_SMTP_AUTH=false
MAIL_SMTP_STARTTLS=false
```

### 0.3 기동

```bash
docker compose up -d          # PostgreSQL (호스트 포트 5434)

cd backend
DB_URL=jdbc:postgresql://localhost:5434/probank_dev ./gradlew bootRun --args='--spring.profiles.active=dev'

cd frontend && npm run dev    # 5173 — /api 와 /uploads 를 모두 8080으로 프록시
```

> **`/uploads` 프록시가 없으면 이미지 미리보기가 전부 404가 난다.** Plan 3에서 추가했으므로 `frontend/vite.config.js`에 `/api`와 `/uploads` 두 항목이 모두 있는지 확인하고 시작할 것.

### 0.4 QA 시작 전 만들어야 하는 데이터

**순서가 중요하다.** 부서가 없으면 계정을 만들 수 없고, 계정이 없으면 부서 격리를 검증할 수 없다.

| 순서 | 작업 | 사용처 | 방법 |
|---|---|---|---|
| 1 | `admin` 로그인 → 강제 비밀번호 변경 | 전체 | 8자 이상, 임시 비밀번호와 달라야 함. **이걸 안 하면 관리자 화면 진입 자체가 안 된다** |
| 2 | 부서 2개 추가 생성 | §2 전체 | `/admin/departments` — 예: `DEV/개발팀`, `SALES/영업팀` |
| 3 | DEPT_ADMIN 2개 생성 | **§2 부서 격리 전용** | 예: `dev_admin`(DEV), `sales_admin`(SALES). **서로 다른 부서여야 격리를 검증할 수 있다** |
| 4 | EMPLOYEE 1개 생성 | §2.9 | 예: `emp001`(SALES) |
| 5 | 각 계정 로그인 → 비밀번호 변경 | 전체 | MailHog에서 임시 비밀번호 확인 후 QA용으로 바꿔 적어 둘 것 |
| 6 | `dev_admin`으로 문제 2건 등록 | §2 | DEV 부서 소유 문제 |
| 7 | `sales_admin`으로 문제 2건 등록 | §2 | SALES 부서 소유 문제 |

6·7번이 끝나면 **서로 다른 부서가 소유한 문제**가 생겨 격리 검증이 가능해진다. 문제 id를 적어 둘 것 — §2에서 URL 직접 입력에 쓴다.

### 0.5 위험 경고 — 운영 DB에서 실행 금지

이 체크리스트에는 **경로 탈출 파일명 업로드, 외부 URL 주입, 권한 우회 API 직접 호출**이 포함된다. 반드시 폐기 가능한 개발 DB·개발 서버에서 수행할 것.

**구현 과정에서 플랜 문서의 코드 자체에 실제 결함 9건이 있었고 전부 수정했다.** 아래는 그중 조용히 재발할 수 있는 것들의 확인이다. 자동 테스트가 덮고 있지만 **화면을 통한 실제 경로로는 확인된 적이 없다.**

| # | 항목 | 절차 | 기대 결과 | 재발 시 영향 |
|---|---|---|---|---|
| 3.1 | **정답 플래그 왕복** ⚠️ | 객관식 문제 등록 → 목록 → 다시 "수정" 열기 | **정답으로 체크했던 보기가 그대로 체크되어 있음** | 자동 매핑으로 되돌아가면 경고 없이 정답이 항상 `false`로 읽혀 **Plan 4 채점이 통째로 틀린다** |

### 8. 엑셀 일괄 업로드 `/admin/problems/excel-upload`

## 알려진 미해결 사항 — QA 중 발견해도 신규 결함이 아님

**재보고 불필요**하되, 실제 사용에 지장이 크다고 판단되면 우선순위 재조정을 요청할 것.

| 항목 | 내용 |
|---|---|
| **보관 복원 불가** | 보관한 문제를 되돌리는 API·UI가 없다. 실수로 보관하면 SQL 없이는 복구 불가. 데이터는 보존됨 |
| 404 에러 코드 | 없는 문제 접근 시 "다시 시도" 버튼이 뜨지만 눌러도 성공하지 않음 (전용 not-found 코드 부재) |
| 페이지네이션 없음 | 목록에 `LIMIT`이 없고 DB 인덱스도 없다. 문제가 수천 건이 되면 느려짐 |
| 태그 필터 위치 | 디자인 8.7은 기본 노출을 명시하나 상세 필터 안에 있음 (백엔드가 단일 태그 문자열만 받음) |
| 태그 입력 방식 | 디자인 8.8은 기존 태그 선택(multi-select)을 시사하나 콤마 입력 + 읽기전용 칩 미리보기 |
| 보관된 문제의 보관 버튼 | 이미 `ARCHIVED`인 행에도 버튼이 보임 (눌러도 무해) |
| 등록일 컬럼 없음 | 등록일로 필터할 수는 있으나 표에 등록일 컬럼이 없어 무엇을 거르는지 눈으로 확인 불가 |
| 이미지 내용 미검증 | 확장자·Content-Type만 검사하고 실제 파일 내용(매직 바이트)은 보지 않음 |
| 엑셀 20MB 안내 누락 | 화면 안내에 파일 크기 상한이 적혀 있지 않음 (서버는 20MB로 제한) |
| 빈 목록 안내 문구 | 필터를 입력만 하고 조회를 누르지 않아도 안내 문구가 바뀔 수 있음 (표시만의 문제) |
| 요청 hang 시 모달 잠김 | Plan 1·2와 동일. `client.js`에 timeout이 없어 응답이 오지 않으면 새로고침이 유일한 탈출구 |
