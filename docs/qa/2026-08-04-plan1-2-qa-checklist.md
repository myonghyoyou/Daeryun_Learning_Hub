## 0. 시작 전 필독 — 환경 준비

### 0.1 SMTP가 없으면 계정 생성 QA를 아예 할 수 없다

`UserAdminServiceImpl.create`는 `insert → mail → audit`를 한 트랜잭션으로 묶는다. **메일 발송이 실패하면 계정 생성 전체가 롤백된다.** 이는 의도된 설계다.

따라서 SMTP 서버 없이 테스트하면 **개별 계정 생성·엑셀 업로드가 100% 실패**한다.

또한 임시 비밀번호는 **응답·화면·로그 어디에도 평문으로 나오지 않는다**(의도된 설계). 즉 QA용으로 만든 계정에 로그인하려면 **메일을 실제로 열어 볼 수단이 반드시 있어야 한다.**

**권장: MailHog** — 받은 메일을 웹 UI에서 바로 볼 수 있어 임시 비밀번호 확인이 가장 빠르다.

```bash
docker run -d --name mailhog -p 1025:1025 -p 8025:8025 mailhog/mailhog
```

백엔드를 아래 환경변수로 기동한다. 받은 메일은 `http://localhost:8025` 에서 확인한다.

```
MAIL_HOST=localhost
MAIL_PORT=1025
MAIL_SMTP_AUTH=false
MAIL_SMTP_STARTTLS=false
```

사내 SMTP 릴레이를 쓸 경우 `MAIL_HOST`, `MAIL_PORT`, `MAIL_USERNAME`, `MAIL_PASSWORD`, `MAIL_SMTP_AUTH`, `MAIL_SMTP_STARTTLS`를 설정한다. 기본값은 `localhost:25`, 인증·STARTTLS 모두 off다.

> MailHog가 떠 있는지 확인: `http://localhost:8025` 접속 → 빈 받은편지함 화면이 보이면 정상.

### 0.3 테스트 계정 준비

#### 0.3.1 준비된 QA 계정 (Docker DB `localhost:5434`, 2026-08-04 기준)

**아래 계정과 부서는 이미 생성해 두었다.** 임시 비밀번호는 MailHog에서 추출한 실제 값이며, 각 계정으로 로그인하면 강제 비밀번호 변경 화면이 먼저 나온다.

> ⚠️ **2026-08-11 확인: 아래 `admin`의 비밀번호가 더 이상 맞지 않는다.** `QaAdmin1234!`로 로그인하면 "사번 또는 비밀번호가 올바르지 않습니다."가 나온다. DB 확인 결과 계정은 `ACTIVE`·잠금 없음이고 실패 카운트만 증가하므로, **다른 환경에서 비밀번호가 교체된 것**으로 보인다. 새 값은 이 저장소 어느 문서에도 없다.
>
> 이 표의 나머지 계정도 같은 이유로 신뢰할 수 없다 — 현재 DB에 실재하는 계정은 `admin`·`dev_admin`·`sales_admin`·`emp001` 4개뿐이고, 표에 적힌 `admin2`·`deptadmin`·`emp002`·`legacy01`은 **존재하지 않는다.**
>
> 관리자가 사용자 비밀번호를 초기화하는 기능이 제품에 없으므로(§0.3.1 아래 참조), 복구하려면 DB의 `users.password_hash`를 직접 갱신해야 한다. 그때는 **반드시 프로젝트 자체의 `BCryptPasswordEncoder`로 해시를 생성하고 `encoder.matches()`로 검증한 뒤** 적용할 것 — 해시를 추측하거나 외부 도구로 만들지 않는다.

| 사번 | 비밀번호 | 이름 | 역할 | 부서 | 최초 로그인 | 로그인 확인 |
|---|---|---|---|---|---|---|
| `admin` | `QaAdmin1234!` | 총괄관리자 | SUPER_ADMIN | HQ | 변경 완료 | ✅ |
| `admin2` | `jKNDhbk2Cw` | 부총괄관리자 | SUPER_ADMIN | DEV | 변경 필요 | ✅ |
| `deptadmin` | `y26HA2ktwC` | 개발팀관리자 | DEPT_ADMIN | DEV | 변경 필요 | ✅ |
| `emp002` | `wXyecVyCtM` | 검증용직원 | EMPLOYEE | SALES | 변경 필요 | ✅ |
| `legacy01` | `yWheGhZjYf` | 폐지팀직원 | EMPLOYEE | **OLD (비활성 부서)** | 변경 필요 | ✅ |
| ~~`emp001`~~ | **불명** | 영업팀직원 | EMPLOYEE | SALES | — | ❌ 사용 불가 |

부서: `HQ/본사`, `DEV/개발팀`, `SALES/영업팀` (활성), **`OLD/폐지팀` (비활성)**

> ⚠️ **`emp001`은 사용하지 말 것.** 메일로 발송된 임시 비밀번호(`u6Tbm9YSBK`)로 로그인이 되지 않는다. 같은 경로로 만든 `emp002`는 정상이고 다른 3개 계정도 정상이므로 재현되지 않는 1회성 이상으로 판단했으나, **원인은 규명하지 못했다.** QA 중 다른 계정에서도 "메일의 임시 비밀번호로 로그인 실패"가 나타나면 즉시 보고할 것 — 그때는 재현 가능한 결함이다.
>
> 참고로 이 상황을 화면에서 복구할 방법이 없다. **관리자가 사용자의 비밀번호를 초기화하는 기능이 없기 때문이다**(계정 수정은 이름·이메일·부서·역할·상태만 다룬다). 사용자가 비밀번호를 잊으면 DB를 직접 손대는 것 말고는 방법이 없다 — 제품 공백으로 별도 기록이 필요하다.

`admin`의 비밀번호를 `QaAdmin1234!`로 바꾼 이유: 비밀번호 변경 전에는 관리자 API가 `1012`로 차단되어(정상 동작) 초기 데이터를 만들 수 없었다. 강제 변경 흐름(§2.7~2.9) 검증은 나머지 계정으로 하면 된다.

이 계정은 하드코딩이 아니라 부트스트랩 설정값이다. `SuperAdminBootstrapRunner`가 기동 시 **활성 SUPER_ADMIN이 하나도 없으면** 아래 값으로 1개를 만든다.

```
BOOTSTRAP_ADMIN_EMPLOYEE_NO   기본 admin
BOOTSTRAP_ADMIN_PASSWORD      기본 changeme1234
BOOTSTRAP_ADMIN_EMAIL         기본 admin@company.local
```

#### 0.3.2 QA 시작 전 만들어야 하는 데이터

`admin` 하나로는 체크리스트의 상당 부분(§3 권한, §4 관리자 보호, §6 비활성 부서 처리)을 진행할 수 없다. **아래 순서대로** 준비할 것. 순서가 중요하다 — 부서가 없으면 계정을 만들 수 없다.

| 순서 | 작업 | 사용처 | 방법 |
|---|---|---|---|
| 1 | `admin` 로그인 → 강제 비밀번호 변경 | 전체 | 8자 이상, 임시 비밀번호와 달라야 함. **이걸 안 하면 관리자 화면 진입 자체가 안 된다** |
| 2 | 부서 3개 생성 | §5, §6, §7 | `/admin/departments` — 예: `DEV/개발팀`, `SALES/영업팀`, `OLD/폐지팀` |
| 3 | `OLD/폐지팀`을 비활성화 | §6.11~6.14 | 비활성 부서가 최소 1개 필요 |
| 4 | 2번째 SUPER_ADMIN 생성 | **§4 전용** | 예: 사번 `admin2`, 부서 `DEV`, 역할 SUPER_ADMIN |
| 5 | DEPT_ADMIN 1개 생성 | §3.3~3.5 | 예: 사번 `deptadmin`, 부서 `DEV` |
| 6 | EMPLOYEE 1개 생성 | §3.2, §6.17 | 예: 사번 `emp001`, 부서 `SALES` |
| 7 | 비활성 부서 소속 계정 1개 | §6.12~6.14 | `OLD` 부서에 계정을 만든 **뒤** 3번을 수행하거나, 3번 후 DB에서 직접 배정 |

**4~6번 계정의 비밀번호는 MailHog(`http://localhost:8025`)에서 확인한다.** 각 계정으로 로그인하면 강제 비밀번호 변경 화면이 뜨므로, QA용 비밀번호로 바꿔 두고 어딘가에 적어 둘 것.

> ⚠️ 7번은 순서에 주의. 비활성 부서에는 **계정을 새로 만들 수 없다**(생성 폼 Select에서 제외된다 — 그것이 §6.11의 검증 대상이다). 따라서 부서가 활성일 때 계정을 먼저 만들고, 그 다음에 부서를 비활성화해야 한다.

#### 0.3.3 준비 완료 확인 (선택)

`psql`로 한 번에 확인할 수 있다. Windows 기본 설치 경로 예시:

```powershell
$env:PGPASSWORD = "probank_dev"
& "C:\Program Files\PostgreSQL\18\bin\psql.exe" -h localhost -p 5432 -U probank -d probank_dev -c `
  "SELECT u.employee_no, u.name, u.role, u.status, d.code AS dept, d.status AS dept_status
   FROM users u JOIN departments d ON d.id=u.department_id ORDER BY u.id;"
```

기대: SUPER_ADMIN 2개(둘 다 ACTIVE), DEPT_ADMIN 1개, EMPLOYEE 1개, 그리고 `dept_status`가 INACTIVE인 계정 1개.

#### 0.3.4 초기화가 필요할 때

QA 도중 관리자 접근을 잃었다면(§4 실패 시나리오), DB에서 직접 복구한다.

```sql
UPDATE users SET role = 'SUPER_ADMIN', status = 'ACTIVE', failed_login_count = 0, locked_until = NULL
WHERE employee_no = 'admin';
```

계정 잠금(§2.3)만 풀려면:

```sql
UPDATE users SET failed_login_count = 0, locked_until = NULL WHERE employee_no = '<사번>';
```

### 0.4 위험 경고 — 운영 DB에서 실행 금지

이 체크리스트에는 **계정 비활성화·역할 강등**이 포함된다. §4.3을 잘못 수행하면 관리자 접근을 잃거나 애플리케이션이 기동하지 않을 수 있다(가드가 그것을 막는지 확인하는 항목이다). 반드시 폐기 가능한 개발 DB에서 수행할 것.
