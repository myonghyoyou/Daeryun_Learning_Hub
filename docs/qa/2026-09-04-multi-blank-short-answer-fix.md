# 다중 빈칸 주관식 4문항 정리 — 작업지시서

- 작성일: 2026-09-04
- 대상 환경: **운영** (`daeryun-learning-hub.vercel.app`), 총괄관리자 로그인 필요
- 성격: **작업지시서. 로컬·운영 어느 쪽 데이터도 아직 수정하지 않았다.**

## 1. 배경

주관식(`SHORT_ANSWER`) 문제 풀이 화면에서, 본문에 빈 괄호 `( )`가 2개 이상 있어도 입력창은 하나뿐이라 "어디에 뭘 입력해야 하는지" 헷갈릴 수 있다는 지적이 있었다.

## 2. 조사 결과

주관식 211문항 전체를 훑어 본문에 `( )`가 2개 이상인 문항 13개를 찾아 하나씩 실제 정답과 대조했다.

| 유형 | 문항 | 실제 상태 |
|---|---|---|
| **진짜 빈칸이 2개 이상인데 정답은 1개뿐** | 181, 186, 317, 632 | 데이터 자체가 불완전 |
| 안내 문구의 "( )"가 괄호 개수를 부풀림 | 182, 270, 502, 528, 554, 597 | 실제 빈칸은 1개뿐, 오탐 |
| 빈칸 여러 개가 전부 같은 정답을 공유 | 345 | 정답은 맞지만 화면상 어색함 |
| 정답 안내 문구가 본문에 그대로 남음 | 441 | 별개의 콘텐츠 결함 |

**정답 구조 자체가 "동의어 인정"용이다.** `problem_answers`의 정답 여러 개는 같은 빈칸을 표현하는 다른 말(예: `메탄`/`CH4`)을 등록하는 것이지, "빈칸 A는 이것, 빈칸 B는 저것"을 담는 구조가 아니다. 관리자 화면에도 명시돼 있다 — *"여러 개를 입력하면 그중 하나만 맞아도 정답으로 처리됩니다."* (`web/screens/admin/problems/ProblemFormPage.jsx:617-622`). 채점 로직(`web/lib/solve/grading.ts:90-98`)도 제출한 답 하나를 정답 목록과 통째로 대조한다.

**원본 소스부터 부족했다.** 4문항(181, 186, 317, 632) 모두 원본 엑셀(`docs/문제은행_엑셀/문제_04_회계팀.xlsx` 등)을 직접 열어 확인한 결과, 임포트 손실이 아니라 문제은행을 만들 때부터 다중 빈칸의 나머지 정답이 채워지지 않았다.

가장 심각한 사례가 632번이다.

```
"단, ( )공사나 도로의 굴착부분의 길이가 ( )미터... ( )미터)... 너비가 ( )미터 이하인 경우는 제출하지 아니할 수 있다."
저장된 정답: "긴급복구"  ← 4개 빈칸 중 첫 번째 것만
```

## 3. 왜 값을 채워 넣지 않았는가

회계팀 전결규정(AA-0200)의 승인 3종류 명칭, 도시가스 온압보정 표준 압력값, 도로굴착 심의 면제 기준 길이·너비 — 이런 것들은 본문에도 지문에도 원본 엑셀에도 근거가 없는 회사 내부 규정·업계 수치다. 일반 지식으로 채우면 실제 직원이 보는 인증 시험에 지어낸 값이 정답으로 박혀 잘못된 규정을 가르치게 되므로, 확인되지 않은 값은 채우지 않았다.

## 4. 유형 변경이 막혀 있다는 것을 확인했다

`FILL_BLANK`로 유형을 바꾸면 빈칸마다 별도 입력창이 나와 문제가 정확히 해결되지만, **기존 문항의 유형은 이 시스템에서 바꿀 수 없다.**

- 관리자 수정 화면: 유형 선택란이 `disabled={isEdit}`이고 옆에 *"문제 유형은 등록 후 변경할 수 없습니다. 다른 유형이 필요하면 새 문제로 등록하세요."* (`ProblemFormPage.jsx:500-502`)
- 서버: `updateProblem()`이 `existing.type !== input.type`이면 예외를 던진다 — `"문제 유형은 수정할 수 없습니다."` (`lib/problem/problemService.ts:195-197`)

정식 경로는 **기존 문항을 보관(archive)하고 같은 내용으로 `FILL_BLANK` 새 문항을 등록**하는 것뿐이다. SQL로 직접 우회하지 않았다 — 화면 문구까지 붙여 의도적으로 만든 규칙이라 판단해서다.

## 5. 번호 재사용이 안 된다는 것도 확인했다

`problems` 테이블의 `uq_problems_department_source_number`는 `(department_id, source_number)`에 걸린 **일반 유니크 제약**이지, `WHERE status='ACTIVE'` 조건이 붙은 부분 인덱스가 아니다. 즉 기존 문항을 보관 처리해도 그 번호는 회수되지 않는다 — 같은 번호로 재등록하면 저장이 거부된다. 그래서 각 문항마다 **새 번호**를 배정했다(아래 표, 운영 DB를 읽기 전용으로 조회해 비어 있는 번호를 확인).

## 6. 작업지시서

**공통 주의사항**

- 재등록 화면에서 **쓰기 모드**를 쓴다. 빈칸이 빈 괄호라 클릭할 단어가 없어 `빈칸 지정 모드`는 못 쓴다.
- **노출 개수는 기본값 1 그대로** 둔다 — 빈칸 후보를 1개만 넣으므로 항상 그 하나가 입력창으로 나온다.
- **본문에 남는 나머지 `( )`는 건드리지 않는다.** 그대로 두면 평범한 텍스트로 남아, 답할 필요 없는 자리라는 게 오히려 더 명확해진다.

**절차 (문항마다 반복)**

1. 문제 관리 목록 → 해당 부서 필터 → 해당 문항 찾기 → **보관** 클릭
2. 새 문제 등록 → 유형 `빈칸 채우기` → 귀속 부서는 원래와 동일 → 아래 표의 본문·번호를 그대로 입력 → 빈칸 후보에 `blank_1` / 정답 입력 → 저장

## 7. 이번에 처리하지 않는 것

**나머지 빈칸(회계팀 승인 2종류, 온압보정 압력값, 도로굴착 기준치 3개)은 여전히 빈 채로 남긴다.** 회사 내부 규정 문서를 갖고 있는 사람이 채워야 풀 수 있는 항목이다. 나중에 값을 알게 되면, 같은 방식으로 `blank_2`, `blank_3` …을 추가하고 노출 개수를 늘리면 된다.

**로컬 DB는 손대지 않았다.** 프로덕션에서 이 작업을 마친 뒤, 다음번 `pnpm sync:problems`를 돌리면 로컬도 같이 반영된다.
