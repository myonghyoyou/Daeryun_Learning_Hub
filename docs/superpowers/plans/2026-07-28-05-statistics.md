> **개정 이력 — 2026-08-13 전면 개정.** 이 계획은 2026-07-28에 작성됐고, 그 뒤 Plan 3·4와 후속 브랜치(관리자 목록 페이징, 빈칸 클릭 지정, 풀이 화면 디자인 시스템 정합, 제출 답안 표시 형식 수정)가 전제를 여러 개 바꿨다. 개정 전 원안을 그대로 실행하면 **오늘의 master 와 충돌하거나 존재하지 않는 코드를 편집하게 된다.** 무엇이 왜 바뀌었는지는 문서 맨 끝 "개정 배경"에 정리했다. 구현자는 그 절을 먼저 읽어라.

**Goal:** 관리자가 문제별 정답률/오답률을 한눈에 보고, 정답률이 낮은 문제를 우선적으로 파악하며, 문제 상세에서 보기별 선택 분포와 최근 오답 샘플까지 확인할 수 있게 한다. 또한 PC 로그인한 관리자가 가장 먼저 보는 관리자 대시보드(`/admin`)를 통계 집계 결과를 재사용해 완성한다.

**Tech Stack:** Plan 1~4와 동일 (Spring Boot 2.7 / MyBatis / PostgreSQL / React 19 / Tailwind CSS 4)

**전제 조건:** Plan 1, Plan 3, Plan 4가 완료되어 있어야 한다. (2026-08-13 기준 모두 master 에 머지됨)

## Global Constraints

이 절의 값은 모든 Task 의 요구사항에 암묵적으로 포함된다.

### 지표 정의

- MVP 핵심 지표는 **문제별 정답률/오답률**이다. 정답률이 낮은 문제를 상위에 정렬한다 (PRD 5.1).
- 부서 관리자는 자기 부서 문제 통계만, 총괄 관리자는 전체(+부서 필터)를 조회한다 (PRD 5.2). 이 범위는 UI가 아니라 **서버가 강제**한다.
- 상세 화면은 총 시도 수/정답 수/정답률/최근 시도일 + 보기별 선택 분포(객관식·OX) + 최근 오답 제출 샘플을 보여준다 (PRD 5.3).
- 개인별/부서별 비교 통계, 응시율, 기간별 추이는 범위 밖이다 (PRD 5.4, 10).

### 보관(ARCHIVED) 문제 처리 — 2026-08-13 결정

보관 확인 Modal 이 사용자에게 "기존 풀이 이력도 그대로 보존됩니다"라고 약속한다. 통계가 보관 순간 시도 수를 잃으면 그 약속을 어긴다. 따라서 **집계에는 포함하고, "고쳐야 할 문제" 판정에서만 제외한다.**

| 지표 | 대상 | 이유 |
|---|---|---|
| 대시보드 `전체 시도 수` | 활성 + 보관 | 학습 활동 총량. 보관해도 줄지 않아야 한다 |
| 대시보드 `평균 정답률` | 활성 + 보관 | 위와 같은 분모를 쓴다 |
| 대시보드 `문제 수` | **활성만** | 지금 관리·출제 가능한 문제 수 |
| 대시보드 `검토 필요 문제` | **활성만** | 보관된 문제는 학습자에게 안 보이므로 고칠 이유가 없다 |
| 대시보드 `정답률이 낮은 문제` 목록 | **활성만** | 위와 같다 |
| 통계 목록 화면 | 활성 + 보관 (상태 필터 제공, 기본 "전체") | 보관 문제의 과거 성적도 조회 가능해야 한다 |

화면은 각 지표 옆에 적용 범위를 문구로 밝힌다(디자인 시스템 8.11 "숫자만 나열하지 않고 적용 범위와 기준을 함께 표시").

### "검토 필요 문제" 정의

**시도 수 5회 이상이면서 정답률 50% 미만인 활성 문제.** 표본이 적은 문제(시도 5회 미만)는 정답률이 낮아도 집계하지 않는다.

`정답률이 낮은 문제` 목록도 **같은 5회 기준을 적용한다.** 두 지표가 다른 기준을 쓰면 "검토 필요 0건"인데 아래 목록은 0%로 가득 찬 화면이 만들어진다(개정 전 계획은 실제로 그 상태를 자기 테스트로 고정하고 있었다).

### 선택지 기록

- 보기 선택 기록은 `attempts.submitted_answer` 문자열이 아니라 **`attempt_choices` 관계 테이블**에 남긴다. `submitted_answer` 는 이력 화면이 그대로 렌더하는 **표시용 텍스트**이며(2026-08-13 `594d05e`), 통계용으로 파싱하지 않는다.
- `attempt_choices.choice_id` 에 **외래키를 걸지 않는다.** 문제를 수정하면 `ProblemServiceImpl.update()` 가 `problemChoiceDao.deleteByProblemId()` 로 선택지를 통째로 지우고 새 ID로 다시 넣는다. `ON DELETE CASCADE` 를 걸면 **문제를 수정할 때마다 풀이 기록이 지워지고**, `RESTRICT` 를 걸면 문제 수정 자체가 막힌다.
- 대신 제출 시점의 `choice_text` 를 함께 스냅샷한다. 문제 수정 뒤에도 "그때 무엇을 골랐는지"는 남는다.

## Design System Implementation Contract

기준 문서는 `docs/superpowers/specs/2026-07-29-blue-bento-design-system.md` 이며 대상 절은 8.6 관리자 Shell·대시보드, 8.11 통계 목록·상세, 9.3 관리자 반응형이다.

- 통계 화면은 관리자 Shell 의 컴팩트한 업무 밀도를 유지한다. 정답률·시도 수·최근 시도일은 숫자만 나열하지 않고 **적용 범위와 기준을 함께** 표시한다.
- 통계 목록은 정답률 낮은 문제 우선 정렬, 부서 필터(총괄만), 상태 필터, 유형 정보가 빠르게 비교되도록 구성한다. 상세는 Summary metric → 보기별 분포 → 최근 오답 샘플 순으로 계층 배치한다.
- 총괄/부서 관리자의 필터 노출 차이를 메뉴·필터·빈 상태에 일관되게 반영한다.
- 로딩 시 Header·필터 위치는 유지하고 metric·표·상세 영역만 Skeleton 처리한다. 데이터 없음·조회 오류·권한 없음·세션 만료 상태와 다음 행동을 제공한다.
- 대시보드(`/admin`, 8.6.2)는 첫 행 4개 compact metric, 둘째 행 정답률 낮은 문제 목록과 최근 문제 등록 활동을 7:5 비율로 배치한다. Primary Action 은 `문제 등록` 하나로 제한하고 부서 선택 필터는 총괄 관리자에게만 노출한다.
- **모바일 접근 차단은 이미 동작한다.** `AdminRoute` 가 `canAccessAdmin({device, role})` 로 막고 `/solve` 로 보낸다. 새로 만들지 말고 **Task 8에서 동작 확인만** 한다.

- [ ] **Step 1: 스키마에 테이블 추가**

`backend/src/main/resources/schema.sql` 의 `attempt_blank_answers` 정의 **바로 아래**에 추가한다:

```sql
-- 객관식/OX 제출에서 고른 보기. attempt_blank_answers 와 대칭 구조다.
--
-- choice_id 에 외래키를 걸지 않는 것은 의도다. 문제를 수정하면 ProblemServiceImpl.update()
-- 가 problem_choices 를 통째로 지우고 새 ID로 다시 넣기 때문에, ON DELETE CASCADE 는
-- 문제를 수정할 때마다 풀이 기록을 지워 버리고 RESTRICT 는 문제 수정을 막는다.
-- 대신 제출 시점의 보기 본문을 함께 남겨, 수정 뒤에도 무엇을 골랐는지는 보존한다.
-- choice_text 가 NULL 인 행은 과거 데이터를 백필하면서 원본 보기를 찾지 못한 경우다.
CREATE TABLE IF NOT EXISTS attempt_choices (
    id BIGSERIAL PRIMARY KEY,
    attempt_id BIGINT NOT NULL REFERENCES attempts(id) ON DELETE CASCADE,
    choice_id BIGINT NOT NULL,
    choice_text VARCHAR(500),
    UNIQUE (attempt_id, choice_id)
);

CREATE INDEX IF NOT EXISTS idx_attempt_choices_choice_id ON attempt_choices(choice_id);
```

```sql
-- 표시 형식 백필(2026-08-13-attempt-answer-summary.sql) 이전에 쌓인 객관식·OX 시도의
-- 보기 선택을 attempt_choices 로 옮긴다. 원본 보기 ID 는 그 백필의 백업 테이블에만 남아 있다.
--
-- 실행:
--   docker exec -i -e PGPASSWORD=probank_dev probank-postgres \
--     psql -U probank -d probank_dev -v ON_ERROR_STOP=1 \
--     < backend/db/backfill/2026-08-13-attempt-choices.sql
--
-- ON CONFLICT DO NOTHING 이라 재실행해도 안전하다.

BEGIN;

WITH parsed AS (
    SELECT b.id AS attempt_id,
           a.problem_id,
           trim(x)::bigint AS choice_id
    FROM attempts_answer_backup_20260813 b
    JOIN attempts a ON a.id = b.id
    JOIN problems p ON p.id = a.problem_id
    CROSS JOIN LATERAL regexp_split_to_table(btrim(b.submitted_answer, '[]'), ',') AS x
    WHERE p.type IN ('MCQ_SINGLE', 'MCQ_MULTI', 'OX')
      AND b.submitted_answer ~ '^\[[0-9, ]*\]$'
      AND trim(x) <> ''
)
INSERT INTO attempt_choices (attempt_id, choice_id, choice_text)
SELECT parsed.attempt_id, parsed.choice_id, c.choice_text
FROM parsed
LEFT JOIN problem_choices c
       ON c.id = parsed.choice_id AND c.problem_id = parsed.problem_id
ON CONFLICT (attempt_id, choice_id) DO NOTHING;

COMMIT;
```

```java
public class ProblemStatItem {
    private Long problemId;
    private String content;
    private ProblemType type;
    private ProblemStatus status;
    private Long departmentId;
    private String departmentName;
    private int totalAttempts;
    private int correctAttempts;
    private Double accuracyRate;
    private LocalDateTime lastAttemptAt;

    public static ProblemStatItem from(ProblemStatRaw raw) {
        Double accuracyRate = raw.getTotalAttempts() == 0
                ? null
                : (double) raw.getCorrectAttempts() / raw.getTotalAttempts();
        return new ProblemStatItem(raw.getProblemId(), raw.getContent(), raw.getType(), raw.getStatus(),
                raw.getDepartmentId(), raw.getDepartmentName(), raw.getTotalAttempts(), raw.getCorrectAttempts(),
                accuracyRate, raw.getLastAttemptAt());
    }
}
```

```java
import com.daeryun.probank.common.AuthUser;
import com.daeryun.probank.dao.AttemptChoiceDao;
import com.daeryun.probank.dao.AttemptDao;
import com.daeryun.probank.dao.ProblemChoiceDao;
import com.daeryun.probank.dao.ProblemDao;
import com.daeryun.probank.dao.StatsDao;
import com.daeryun.probank.domain.UserRole;
import com.daeryun.probank.dto.stats.ProblemStatItem;
import com.daeryun.probank.dto.stats.ProblemStatPageResponse;
import org.springframework.stereotype.Service;

import java.util.Comparator;
import java.util.List;
import java.util.stream.Collectors;

@Service
public class StatsServiceImpl implements StatsService {

    /**
     * 정답률 오름차순, 미응시(null)는 맨 뒤, 동률은 problemId 로 끊는다.
     *
     * <b>정렬의 근거는 SQL 이다</b>(StatsMapper 의 accuracyOrder). 페이징이 그 순서 위에서
     * 잘리기 때문에 자바에서만 정렬하면 페이지 안에서만 맞고 전체로는 틀린다. 이 비교자는
     * 같은 규칙을 자바로 다시 적어 <b>의도를 단위 테스트로 고정</b>하는 역할이며, 이미 정렬된
     * 페이지에 다시 적용해도 결과가 바뀌지 않는다(no-op).
     *
     * 두 곳 중 한쪽만 고치면 페이지 안과 밖의 순서가 어긋난다. 반드시 함께 고쳐라.
     */
    private static final Comparator<ProblemStatItem> LOWEST_ACCURACY_FIRST =
            Comparator.comparing(ProblemStatItem::getAccuracyRate, Comparator.nullsLast(Comparator.naturalOrder()))
                    .thenComparing(ProblemStatItem::getProblemId);

    private final StatsDao statsDao;
    private final AttemptDao attemptDao;
    private final AttemptChoiceDao attemptChoiceDao;
    private final ProblemDao problemDao;
    private final ProblemChoiceDao problemChoiceDao;

    public StatsServiceImpl(StatsDao statsDao, AttemptDao attemptDao, AttemptChoiceDao attemptChoiceDao,
                            ProblemDao problemDao, ProblemChoiceDao problemChoiceDao) {
        this.statsDao = statsDao;
        this.attemptDao = attemptDao;
        this.attemptChoiceDao = attemptChoiceDao;
        this.problemDao = problemDao;
        this.problemChoiceDao = problemChoiceDao;
    }

    /**
     * 총괄 관리자는 요청한 부서를, 부서 관리자는 요청값을 무시하고 자기 부서를 쓴다.
     * 이 스코프는 UI 가 아니라 여기서 강제된다.
     */
    private Long effectiveDepartmentId(AuthUser actor, Long requested) {
        return actor.getRole() == UserRole.SUPER_ADMIN ? requested : actor.getDepartmentId();
    }

    @Override
    public ProblemStatPageResponse listProblemStats(AuthUser actor, Long departmentId, String status, int page, int size) {
        Long scope = effectiveDepartmentId(actor, departmentId);
        int safePage = Math.max(1, page);
        List<ProblemStatItem> items = statsDao.findProblemStats(scope, status, size, (safePage - 1) * size).stream()
                .map(ProblemStatItem::from)
                .sorted(LOWEST_ACCURACY_FIRST)
                .collect(Collectors.toList());
        return new ProblemStatPageResponse(items, statsDao.countProblemStats(scope, status), safePage, size);
    }

    @Override
    public List<ProblemStatItem> listAllProblemStats(AuthUser actor, Long departmentId) {
        return statsDao.findAllProblemStats(effectiveDepartmentId(actor, departmentId)).stream()
                .map(ProblemStatItem::from)
                .sorted(LOWEST_ACCURACY_FIRST)
                .collect(Collectors.toList());
    }

    @Override
    public int countActiveProblems(AuthUser actor, Long departmentId) {
        return statsDao.countActiveProblems(effectiveDepartmentId(actor, departmentId));
    }
}
```

```java
package com.daeryun.probank.service;

import com.daeryun.probank.common.AuthUser;
import com.daeryun.probank.dao.ProblemDao;
import com.daeryun.probank.domain.ProblemStatus;
import com.daeryun.probank.domain.UserRole;
import com.daeryun.probank.dto.dashboard.DashboardSummaryResponse;
import com.daeryun.probank.dto.problem.ProblemListItem;
import com.daeryun.probank.dto.stats.ProblemStatItem;
import org.springframework.stereotype.Service;

import java.util.List;
import java.util.stream.Collectors;

@Service
public class DashboardServiceImpl implements DashboardService {

    private static final int MIN_ATTEMPTS_FOR_REVIEW = 5;
    private static final double REVIEW_ACCURACY_THRESHOLD = 0.5;
    private static final int LOW_ACCURACY_LIST_SIZE = 5;
    private static final int RECENT_PROBLEM_LIST_SIZE = 5;

    private final StatsService statsService;
    private final ProblemDao problemDao;

    public DashboardServiceImpl(StatsService statsService, ProblemDao problemDao) {
        this.statsService = statsService;
        this.problemDao = problemDao;
    }

    /**
     * "지금 고쳐야 할 문제"의 단일 정의. 검토 필요 건수와 정답률 낮은 문제 목록이 같은
     * 함수를 쓰지 않으면 "검토 필요 0건"인데 목록은 0% 로 가득 찬 화면이 만들어진다.
     */
    private boolean needsReview(ProblemStatItem item) {
        return item.getStatus() == ProblemStatus.ACTIVE
                && item.getTotalAttempts() >= MIN_ATTEMPTS_FOR_REVIEW
                && item.getAccuracyRate() != null
                && item.getAccuracyRate() < REVIEW_ACCURACY_THRESHOLD;
    }

    @Override
    public DashboardSummaryResponse getSummary(AuthUser actor, Long departmentId) {
        // StatsService 가 부서 스코프를 강제하지만 ProblemDao.findRecent 는 원시 DAO 라
        // 스스로 강제하지 않는다. 같은 규칙으로 유효 부서 ID 를 계산해 넘긴다.
        Long effectiveDepartmentId = actor.getRole() == UserRole.SUPER_ADMIN ? departmentId : actor.getDepartmentId();

        List<ProblemStatItem> allStats = statsService.listAllProblemStats(actor, departmentId);

        int totalAttempts = allStats.stream().mapToInt(ProblemStatItem::getTotalAttempts).sum();
        int totalCorrectAttempts = allStats.stream().mapToInt(ProblemStatItem::getCorrectAttempts).sum();
        Double averageAccuracyRate = totalAttempts == 0 ? null : (double) totalCorrectAttempts / totalAttempts;

        List<ProblemStatItem> reviewTargets = allStats.stream()
                .filter(this::needsReview)
                .collect(Collectors.toList());

        // allStats 는 StatsServiceImpl 에서 이미 정답률 오름차순으로 정렬돼 있으므로 재정렬하지 않는다.
        List<ProblemStatItem> lowAccuracyProblems = reviewTargets.stream()
                .limit(LOW_ACCURACY_LIST_SIZE)
                .collect(Collectors.toList());

        List<ProblemListItem> recentProblems = problemDao.findRecent(effectiveDepartmentId, RECENT_PROBLEM_LIST_SIZE);

        return new DashboardSummaryResponse(
                statsService.countActiveProblems(actor, departmentId),
                reviewTargets.size(),
                totalAttempts,
                totalCorrectAttempts,
                averageAccuracyRate,
                lowAccuracyProblems,
                recentProblems);
    }
}
```

```javascript
export function formatAccuracyRate(rate) {
  if (rate === null || rate === undefined) {
    return "미응시";
  }

}

/**
 * "지금 고쳐야 할 문제"인지. 서버 DashboardServiceImpl.needsReview 와 같은 조건이며,

export function isReviewNeeded(item) {
```

# 개정 배경 (2026-08-13)

원안은 2026-07-28에 작성됐다. 그 뒤 master 가 달라진 부분과, 그래서 무엇을 바꿨는지다.

### 1. `attempts.submitted_answer` 의 성격이 바뀌었다

원안 Task 1은 이 컬럼을 **정렬된 보기 ID 문자열**(`10,11`)로 만들어 Task 3이 파싱하게 했다. 그러나 2026-08-13 `594d05e` 가 이 컬럼을 **이력 화면에 그대로 렌더되는 표시용 텍스트**(`Java, Python`)로 확정했다 — 그 전에는 `[104]` 가 사용자에게 노출되고 있었다.

한 컬럼이 표시와 집계를 동시에 맡을 수 없어 `attempt_choices` 관계 테이블을 도입했다. 결과적으로 **원안보다 낫다**: 문자열 파싱이 없고, 다중 선택 순서 문제가 사라지고, 보기 문구 수정에도 견딘다.

부수 효과로 원안의 승인 수정사항 중 "객관식 최근 오답 샘플을 보기 번호/텍스트로 변환한다"와 `RecentWrongSample.displayAnswer` 가 **불필요해져 삭제**했다.

### 2. 관리자 메뉴 구조가 바뀌었다

원안은 `AdminLayout.jsx` 의 `NAV_ITEMS` 배열을 교체하라고 지시하지만 **그 상수는 더 이상 없다.** 지금은 `utils/adminNav.js` 의 `buildNavGroups(role)` 가 역할별로 메뉴를 만들고 `adminNav.test.js` 가 `end` 접두사 규칙까지 검사한다.

### 3. 관리자 목록이 서버 페이징으로 바뀌었다

2026-08-09 브랜치가 문제 목록에 `limit/offset` + `countAll` + `Pagination` 을 넣었다. 통계 목록만 전건을 내려받으면 화면 일관성이 깨진다. Task 2에 페이징을 넣었다.

### 4. 빈칸 채우기가 생겼다

문제 본문에 `{{b1}}` 마커가 저장된다. 원안은 `item.content` 를 그대로 출력해 **관리자 화면에 내부 마커가 노출**된다. `previewContent()` 로 바꿨다.

### 5. 디자인 시스템 구현이 완성됐다

원안의 프론트엔드 코드는 Tailwind 기본 팔레트(`text-gray-500`, `bg-blue-600`, `rounded border`)로 쓰여 있어 `tokens.css` 가 금지한 것을 정면으로 어긴다. Plan 4 이후 `Surface`·`DataTable`·`Button`·`ListStateSurface`·`Pagination`·`buttonClass` 가 모두 갖춰졌고, 세 화면을 그 부품 위에 다시 썼다.

### 6. 지표 정의의 자기모순을 고쳤다

원안은 `검토 필요 문제`에는 "시도 5회 이상" 기준을 걸면서 `정답률이 낮은 문제` 목록에는 걸지 않았다 — **자기 테스트가 그 모순을 고정하고 있었다**(시도 3건짜리 0% 문제가 목록 1위인데 검토 필요에서는 제외). `DashboardServiceImpl.needsReview()` 하나로 두 지표를 통일했다.

### 7. 보관 문제 처리를 명시했다 (2026-08-13 결정)

원안은 `WHERE p.status = 'ACTIVE'` 로 보관 문제를 통째로 뺐다. 그러면 문제를 보관하는 순간 대시보드의 시도 수와 평균 정답률이 소리 없이 줄어드는데, 보관 확인 Modal 은 "기존 풀이 이력도 그대로 보존됩니다"라고 약속한다. 집계에는 포함하고 "고쳐야 할 문제" 판정에서만 제외하도록 바꿨다.

### 8. 개정판 자체 검토에서 다시 고친 것 (2026-08-13 2차)

개정판을 코드베이스와 한 번 더 대조해 여섯 건을 고쳤다.

- **페이징이 정렬을 깨고 있었다(가장 큰 것).** 개정 1차는 SQL 을 `ORDER BY p.id` 로 자르고 서비스가 그 20건만 정답률로 정렬했다. 그러면 **전체에서 정답률이 가장 낮은 문제가 3페이지에 남아** 이 Plan 의 핵심 요구가 깨진다. 정렬을 SQL(`accuracyOrder`)로 올리고, 자바 비교자는 같은 규칙을 단위 테스트로 고정하는 역할로 격하했다. 두 곳이 어긋나면 페이지 안에서만 맞는 상태가 되므로 Task 8에 **페이지를 넘어가는 정렬 확인**을 넣었다.
- **`adminNav.test.js` 의 기존 테스트 세 개가 깨진다.** 그 파일에는 메뉴 전체를 `deepEqual` 로 고정한 테스트가 둘 있고, `no menu item points at /admin while the dashboard screen does not exist` 는 대시보드가 생기면 **이름과 주석이 거짓**이 된다. 개정 1차는 신규 테스트 추가만 지시했다 → Task 7 Step 2를 (a) 기존 배열 갱신 (b) 이름·주석 정정 (c) 신규 추가로 나눴다.
- **`TableCell` 이 `title` 을 버린다.** 나머지 props 를 전달하지 않아 툴팁이 뜨지 않는다. `ProblemListPage.jsx:230` 이 이미 `title` 을 넘기고 있고 **그 prop 은 지금 아무 일도 하지 않는다.** Task 6 Step 1에서 고친다.
- **`StatusBadge` 에 `ARCHIVED` 스타일이 없다.** 기본 분기(회색)로 떨어져 결과는 괜찮지만 아무도 결정한 적 없는 색이다. 보관 문제를 통계 목록에 1급으로 노출하는 이번 Plan 에서 의도를 코드에 남긴다.
- **`Mockito.when()` 으로 void 메서드를 스텁하고 있었다.** `AttemptDao.insert` 는 void 라 `doAnswer(...).when(...)` 을 써야 컴파일된다.
- **테스트 import 스타일이 저장소와 달랐다.** `import test from "node:test"` → `import { test } from "node:test"`.

또한 확인만 하고 바꾸지 않은 것: **`AdminRoute` 가 세션 로딩 중에는 `Loader` 만 그리고 자식을 렌더하지 않는다.** 그래서 관리자 화면 안에서는 `session` 이 항상 non-null 이며, 방어 코드를 넣을 필요가 없다는 사실을 Task 6·7에 명시했다.

### 9. 그 밖의 정정

- 컨트롤러가 `HttpServletRequest` + `SessionKeys` 로 로그인 사용자를 꺼내고 있었다 → 기존 6개 컨트롤러와 같은 `@LoginUser AuthUser actor` 로 통일.
- `getProblemDetail` 이 한 문제의 요약을 얻으려 부서 전체를 집계하고 `findByProblemId` 를 두 번 호출했다 → `StatsDao.findProblemStat(problemId)` 추가, 중복 호출 제거.
- 보기 ID 파싱에 가드가 없어 `NumberFormatException` 위험이 있었다 → `attempt_choices` 도입으로 파싱 자체가 사라졌다.
- `StatsMapper.xml` 에 `ORDER BY` 가 없어 페이징과 함께 쓰면 중복·누락이 생긴다 → `ORDER BY p.id` 와 정렬 타이브레이커 추가.
- 화면마다 `formatRate` 를 복제하고 있었다 → 테스트 가능한 `utils/statsFormat.js` 로 통합.
- Design Contract 는 있는데 그것을 수행하는 Task 가 없었다 → **Task 8 신설.**
- "모바일 접근 차단"은 이미 `AdminRoute` 가 하고 있다 → 신규 구현이 아니라 확인 항목으로 격하.
- Step 별 "N tests 통과" 기대값이 이미 어긋나 있었다(원안 "11 tests" → 현재 `SolveServiceImplTest` 는 20건) → 건수 대신 `BUILD SUCCESSFUL` 과 신규 테스트 이름으로 표기.
