# 제작자 피드백 전달 설계

**작성일:** 2026-09-04
**참조:** 받는 쪽 명세 아티팩트 「DR Learning hub 피드백 연결」 (Por favor, Harry `7187aa6` → `3bbaaaa`)

## 1. 배경과 목표

문제은행 Hub 를 쓰는 사람이 남긴 말을 제작자의 업무 보드로 보낸다.

받는 쪽 문은 이미 열려 있고, 이 문서는 **보내는 쪽**에서 만들 것을 적는다.

특히 이 서비스에는 보낼 말이 실제로 쌓여 있다. 종이 문제집을 옮겨 온 문제은행이라
OCR 손상이 남아 있고(661번의 깨진 글자, 보기에 섞여 들어간 `※ 다음 빈칸에 알맞은 단어를
쓰시오`, 2026-09-04 에 고친 괄호 안 정답 노출 3건), **그런 것을 가장 먼저 발견하는 사람은
문제를 푸는 사람이다.** 지금은 그 발견을 주워 담을 통로가 없다.

## 2. 외부 계약

아래 표가 유일한 명세다. 우리가 바꿀 수 없다.

```
POST <HARRY_INBOUND_URL>
Authorization: Bearer <HARRY_INBOUND_SECRET>
Content-Type: application/json

{ "body": "...", "from": "홍길동(emp_01)" }
```

| 필드 | 필수 | 규칙 |
|---|---|---|
| `body` | 필수 | 앞뒤 공백을 뗀 뒤 1~2000자. **첫 줄이 업무 제목이 되고 60자에서 잘린다.** 원문은 메모에 전부 남는다 |
| `from` | 선택 | 40자에서 잘린다. 없거나 공백이면 받는 쪽이 `익명` 으로 적는다 |

| 응답 | 뜻 |
|---|---|
| 201 | `{ ok: true, taskId }` — 보드에 카드가 생겼다 |
| 400 | 본문이 규칙에 안 맞는다. **한도를 쓰지 않는다** |
| 401 | 비밀이 틀렸다 |
| 429 | 시간당 한도(100)를 넘었다 |
| 500 | 받는 쪽 설정이 빠졌다 |

**제약 세 가지를 설계 전체가 떠안는다.**

- **CORS 헤더가 일부러 없다.** 브라우저에서 직접 부를 수 없다
- **한도는 시간당 100건이고 서비스 전체가 하나를 공유한다.** 사람별이 아니다
- **중복 판정이 없다.** 두 번 보내면 카드가 둘 생기고 지우는 것은 사람 몫이다

## 3. 이 저장소에 맞춘 구조

아티팩트는 서버 액션(`app/feedback/actions.ts`)으로 그렸지만 **이 저장소에는 서버 액션이
하나도 없다**(`grep '"use server"'` 결과 0건). 인증도 NextAuth 가 아니라 자체 JWT 다.
계약만 지키고 구현 형태는 이 저장소 관용구를 따른다.

```
브라우저                     우리 서버                      받는 쪽
─────────                   ─────────                      ─────────
FeedbackModal        →      POST /api/feedback       →     인바운드 라우트
비밀을 모른다               비밀이 사는 유일한 곳            카드 하나 생성
                            저장 → 전달 → 결과 기록
```

가운데 층을 건너뛸 수 없다. 비밀이 브라우저로 내려가는 순간 누구나 이 프로젝트에 업무를
만들 수 있다.

**`server-only` 패키지를 새로 넣는다.** 클라이언트 컴포넌트가 실수로 비밀 모듈을 import
하면 빌드가 깨져서 알려 준다. 사람의 주의력에 기대지 않는다.

## 4. 데이터 모델

먼저 저장하고 그다음 전달한다. 받는 쪽이 죽어 있어도 말은 남고 나중에 다시 밀 수 있다.

```sql
feedbacks
  id            bigserial    PK
  user_id       bigint       NOT NULL → users.id
  problem_id    bigint       NULL     → problems.id      -- 문제별 신고면 채워짐
  source_path   varchar(200) NULL                        -- 보던 화면 경로
  body          text         NOT NULL                    -- 사용자 원문 (조립 전)
  status        varchar(20)  NOT NULL DEFAULT 'PENDING'  -- PENDING|SENT|FAILED
  fail_reason   varchar(20)  NULL                        -- config|invalid|busy|down
  task_id       varchar(100) NULL                        -- 성공 시 받은 값
  attempt_count integer      NOT NULL DEFAULT 0
  last_tried_at timestamp    NULL
  created_at    timestamp    NOT NULL DEFAULT now()

  CHECK (status IN ('PENDING','SENT','FAILED'))
  CHECK (fail_reason IS NULL OR fail_reason IN ('config','invalid','busy','down'))
  INDEX (status, created_at)   -- 실패 목록 조회용
```

**원문만 저장하고 조립본은 저장하지 않는다.** 다시 보낼 때 그 시점 규칙으로 다시 조립하는
편이 낫고, 같은 사실을 두 벌 두면 한쪽만 고쳐지는 사고가 난다.

**`problem_id` 에 `ON DELETE SET NULL` 을 건다.** 문제가 지워졌다고 그 문제에 대한 의견까지
지울 이유가 없다 — 오히려 왜 지웠는지 아는 단서다.

### 상태 변화

```
PENDING ──전달 성공──→ SENT    (끝. 다시 보내지 않는다)
   │
   └────전달 실패──→ FAILED ──다시 보내기──→ SENT 또는 FAILED
```

`PENDING` 은 저장은 됐는데 전달 결과를 아직 못 받은 상태다. 정상 흐름에서는 순식간에
지나가지만, 서버가 전달 중에 죽으면 여기 남는다. **실패 목록은 `status <> 'SENT'` 로
잡는다** — `FAILED` 만 보면 그렇게 남은 것을 영영 못 찾는다.

## 5. API

### `POST /api/feedback`

```
요청  { body: string, problemId?: number, sourcePath?: string }
응답  { ok: boolean, message: string }
```

라우트는 이 저장소 관용구를 그대로 따른다(`app/api/attempts/me/route.ts` 참고).

```ts
export const runtime = "nodejs";

export async function POST(request: Request): Promise<Response> {
  return handleRoute(async () => {
    const actor = await requireActor();   // 역할 제한 없음 — 누구나 보낸다
    ...
  });
}
```

**문제 정보와 태그는 서버가 직접 만든다.** 화면은 `problemId` 만 넘기고, 부서 이름·번호·
유형은 서버가 DB 에서 찾는다. 화면이 만들어 보낸 문자열을 그대로 실으면 조작할 수 있고,
문제가 수정됐을 때 화면과 보드의 표기가 갈린다.

태그도 서버가 정한다 — `problemId` 가 있으면 `[부서 N번]`, 없고 `sourcePath` 가 `/admin`
으로 시작하면 `[관리자]`, 그 밖에는 `[학습]`.

**검증을 우리가 먼저 한다.** 받는 쪽도 같은 것을 막지만, 400 을 받아 번역하는 것보다
사용자에게 바로 말하는 편이 빠르고 **잘못된 요청이 남의 한도를 먹지 않는다.**

- `body` 앞뒤 공백을 뗀 뒤 1~1000자 (아래 6절의 길이 예산)
- `problemId` 가 있으면 실재하는 문제인지 확인한다. 없는 id 면 문제 정보 없이 일반 의견으로 처리한다 — 본문은 멀쩡한데 참조 하나 때문에 말을 버리지 않는다
- `sourcePath` 는 200자에서 자르고, `/` 로 시작하지 않으면 버린다(외부 URL 이 섞여 들어오는 것을 막는다)

### `GET /api/admin/feedbacks?status=unsent`

전달 실패 목록. **총괄 관리자 전용.** 이유는 9절에 적었다.

### `POST /api/admin/feedbacks/retry`

다시 보내기. 총괄 관리자 전용. 한 번에 **최대 20건**, **429 를 만나면 즉시 중단**한다.
한도가 서비스 전체 공유라, 실패한 것을 한꺼번에 밀면 그 시간대의 정상 제출이 막힌다.

## 6. 본문 조립

**첫 줄이 업무 제목이 되고 60자에서 잘린다.** 이 한 줄이 보드에서 그 카드를 알아보는
유일한 단서다.

### 태그로 출처를 가른다

```
[자금팀 26번] 괄호 안에 답이 그대로 보입니다      ← 문제별 신고
[학습] 엔터로 다음 칸 넘어가는 게 안 됩니다        ← 학습 화면 일반 의견
[관리자] 통계에서 부서 필터가 초기화됩니다          ← 관리자 화면
```

`[부서 N번] ` 태그가 약 10자라 **사용자가 쓴 첫 줄이 50자까지 제목에 살아남는다.**
태그만 붙이고 사용자 문장을 빼면 제목이 전부 `[자금팀 26번] 문제 신고` 가 되어 보드에서
구분이 안 된다.

### 전체 모양

문제별 신고:

```
[자금팀 26번] 괄호 안에 답이 그대로 보입니다

문제 260 · 주관식 · 자금팀 26번
화면: /solve/problems/188/play

괄호 안에 답이 그대로 보입니다. 문제를 읽자마자 정답을 알 수 있어요.
```

일반 의견:

```
[학습] 엔터로 다음 칸 넘어가는 게 안 됩니다

화면: /solve/problems/188/play

엔터로 다음 칸 넘어가는 게 안 됩니다. 빈칸이 두 개일 때만 그런 것 같아요.
```

첫 줄이 제목과 메모에 두 번 나오는데 **의도한 중복이다.** 받는 쪽은 본문 전체를 메모로
남기므로, 원문을 온전히 보존하려면 이 편이 안전하다.

### 길이 예산

| | 값 |
|---|---|
| 계약 상한 | 2000자 |
| 우리가 붙이는 머리말 | 최대 약 150자 |
| **사용자 입력 상한** | **1000자** |

입력 상한을 1000자로 두면 조립 후에도 여유가 크다. **서버에서 조립 후 2000자를 다시
확인하고**, 넘으면 사용자 원문 끝을 자른다(머리말은 자르지 않는다 — 자르면 문제 참조가
사라져 카드가 쓸모없어진다).

### 보낸 사람

```
from = `${name}(${employeeNo})`     예: 기획팀직원(plan_emp)
```

40자를 넘으면 **`(사번)` 을 그대로 두고 이름 쪽을 잘라** 전체가 40자에 맞게 한다.
사번이 잘리면 되묻는 길이 끊긴다.

이름과 사번만. **이메일과 내부 id 는 넣지 않는다** — 이 값은 남의 업무 메모 첫 줄이 되고
여러 명이 본다. 40자를 넘으면 **사번을 살리고 이름을 줄인다.** 되묻기에 필요한 것은
사번이다.

이 서비스에는 비로그인 경로가 없으므로(모든 화면이 `(protected)` 아래) `from` 은 항상
채워진다. 받는 쪽의 `익명` 분기는 우리에게 오지 않는다.

## 7. 화면

진입점은 넷이고 **모달 하나와 API 하나를 공유한다.** 화면마다 폼을 따로 만들면 한쪽만
고쳐지는 사고가 난다.

```
학습   ├ 문제 카드 머리 오른쪽   → 문제별 신고   [부서 N번]
       ├ 학습 홈 카드            → 일반 의견     [학습]
       └ 셸 바닥 링크            → 일반 의견     [학습]

관리자 └ 사이드바 「피드백」      → 일반 의견     [관리자]
```

### 공통 모달

이미 있는 `components/ui/Modal.jsx` 를 쓴다. 포커스 이동·복귀와 `dismissible=false` 가
구현돼 있다. **보내는 동안 `dismissible=false` 로 잠근다** — 중복 판정이 없으므로 두 번
눌린 만큼 카드가 생긴다.

- `textarea` 는 `value`/`onChange` 로 글자를 직접 들고 있는다
- **성공했을 때만 비운다.** 실패했는데 지우면 방금 쓴 글이 사라진다
- 남은 글자 수를 보여 준다(1000자 상한)

### 문제 카드 신고 버튼

문제 카드 머리(유형 칩 · 출처 배지 줄) 오른쪽 끝에 작은 버튼을 둔다.
**채점 전후 모두 열려야 한다** — 틀리고 나서야 문제가 이상하다는 것을 아는 경우가 많다.

### 셸 바닥 링크

`SolveShell` 의 `<main>` 아래에 조용한 한 줄. **불편을 느낀 그 자리에서** 바로 열 수 있는
것이 중요하다. 홈에만 두면 되돌아가야 하고, 그러면 대부분 그냥 넘어간다.

**헤더에는 넣지 않는다.** `SolveShell` 주석에 "모바일 헤더는 이미 제목+로그아웃으로 폭이
빠듯해 실측 검증(design QA)을 마친 레이아웃"이라고 적혀 있다.

### 학습 홈 카드

기존 벤토 3개와 명예의 전당 아래, 한 줄짜리 얇은 카드.

### 관리자 피드백 화면

- 사이드바에 `피드백` 항목 추가 — `utils/adminNav.js` 의 `buildNavGroups`. 접두사 규칙
  테스트(`adminNav.test.js`)가 이미 붙어 있으므로 `end` 규칙을 지켜야 한다
- 두 관리자 역할 모두에게 **보내기**를 노출한다
- **전달 실패 목록과 다시 보내기는 총괄 관리자에게만** 보인다

## 8. 실패 처리

| 응답 | 사용자에게 보이는 말 | 우리가 하는 일 |
|---|---|---|
| 201 | 보냈습니다. 고맙습니다. | `SENT` + `task_id` |
| 400 | 지금은 보낼 수 없습니다. 잠시 뒤 다시 시도해 주세요. | **우리 검증이 샜다는 뜻.** `FAILED(invalid)` + 로그에 원문 |
| 401 | 같음 | `FAILED(config)` + 로그 |
| 429 | 지금 접수가 몰려 있습니다. 잠시 뒤 다시 보내 주세요. | `FAILED(busy)` |
| 500 · 시간초과 · 네트워크 | 지금은 보낼 수 없습니다. | `FAILED(down)` |
| 설정 없음 | 같음 | `FAILED(config)`. **보내는 척하지 않는다** |

**5초에서 끊는다.** 기본 `fetch` 는 무한정 기다려서, 받는 쪽이 느리면 우리 요청 하나가
통째로 물린다 — 남의 장애를 내 장애로 옮기지 않는다.

**받는 쪽 오류 문구를 사용자에게 그대로 보이지 않는다.** 내부 설정 이름과 한도 숫자가
새고, 읽어도 사용자가 할 수 있는 것이 없다. 원문은 로그로만 남긴다.

**저장이 실패하면 전달하지 않는다.** 저장 없이 보내면 실패했을 때 아무 데도 남지 않는다.

## 9. 정한 것과 그 이유

| 정한 것 | 이유 |
|---|---|
| DB 에 먼저 넣고 전달 | 받는 쪽이 죽어도 말이 남는다. 관리자 화면이 볼 것이 생긴다 |
| `from` 은 이름+사번 | 되묻기에 필요한 것은 사번. 이메일은 남의 보드에 있을 이유가 없다 |
| 문제별 신고와 일반 의견을 나눔 | 합치면 "이건 문제 얘기가 아닙니다"를 사용자가 매번 적어야 한다 |
| 실패 목록은 총괄 관리자만 | 피드백은 부서를 가로지르는 데이터다. 부서 관리자에게 보이면 "부서 관리자는 자기 부서 데이터만 본다"는 원칙이 깨진다 |
| 다시 보내기 20건 · 429 면 중단 | 한도가 서비스 전체 공유라, 한꺼번에 밀면 그 시간대의 정상 제출이 막힌다 |

## 10. 테스트

순수 함수로 뽑아 두고 거기에 테스트를 건다.

| 대상 | 확인할 것 |
|---|---|
| `composeFeedbackBody` | 세 태그 갈래, 첫 줄이 60자 안에서 뜻을 유지하는지, 조립 후 2000자 상한 |
| `composeFrom` | 40자 초과 시 **사번이 살아남는지** |
| `validateFeedbackInput` | 공백만, 0자, 1001자, `sourcePath` 가 `/` 로 시작하지 않을 때 |
| 라우트 | `fetch` 를 가짜로 두고 201·400·401·429·타임아웃 다섯 갈래가 각각 어떤 `status`·`fail_reason`·문구가 되는지 |
| DAO | 실패 목록이 `status <> 'SENT'` 로 잡히는지(`PENDING` 이 빠지지 않는지) |

## 11. 환경변수와 배포 순서

```
HARRY_INBOUND_URL=https://<받는쪽-도메인>/api/inbound/feedback
HARRY_INBOUND_SECRET=<받는 쪽 INBOUND_SECRET 과 같은 값>
```

**`NEXT_PUBLIC_` 을 절대 붙이지 않는다.** 붙는 순간 번들에 실려 나간다.

붙이는 순서는 아티팩트가 권한 대로 한다. **두 쪽을 동시에 의심하지 않기 위해서다.**

1. 받는 쪽 Vercel 에 `INBOUND_SECRET` · `INBOUND_FEEDBACK_PROJECT` 를 넣고 **재배포**한다
   (환경변수는 빌드 시점에 구워지므로 추가만 하고 재배포를 안 하면 반영되지 않는다).
   `curl` 로 201 을 눈으로 확인한다
2. 우리 로컬에서 전달 모듈과 라우트까지. 화면 없이 201·400·401 세 갈래를 확인한다
3. 마이그레이션을 개발 DB 에 적용한다
4. 모달을 붙이고 **실패를 일부러 만든다.** 비밀을 한 글자 바꿔 401 을, URL 을 죽은 주소로
   바꿔 시간초과를. **그때 사용자가 쓴 글이 남아 있는지가 이 연동에서 가장 중요한 확인이다**
5. 운영 마이그레이션(`pnpm migrate:prod`) 후 배포. 한 건 보내 보드에 카드가 뜨는지 본다

## 12. 범위 밖

- **되묻기.** 지금은 한 방향이다. 제작자가 처리해도 그 사실이 사용자에게 돌아오지 않는다.
  필요해지면 그때 설계할 일이지 지금 만들 것이 아니다
- **본격적인 수신함.** 목록·검색·상태 관리·담당자 지정은 받는 쪽 보드가 할 일이다.
  우리 관리자 화면은 **전달 실패한 것만** 보여 준다
- **첨부 파일·화면 캡처.** 계약이 글자만 받는다
- **자동 재전송.** 실패한 것을 주기적으로 다시 미는 장치는 두지 않는다. 한도가 서비스
  전체 공유라 자동화가 조용히 한도를 먹으면 정상 제출이 막힌다. 사람이 눌러서 보낸다

## 13. 알려진 한계

- **한도가 시간당 100건이고 서비스 전체가 공유한다.** 공지 직후처럼 몰리면 그 시간대의
  모두가 429 를 맞는다. 다만 우리 DB 에 남으므로 **의견이 사라지지는 않는다.**
  사용자 수가 늘면 받는 쪽에서 이 숫자를 올려야 한다
- **중복 판정이 받는 쪽에 없다.** 버튼 잠금으로 막지만, 새로고침 후 같은 말을 다시 보내면
  카드가 둘 생긴다. 우리 DB 에는 두 행이 남으므로 사후 확인은 가능하다
- **`PENDING` 으로 남는 경우가 있다.** 저장 뒤 전달 중에 서버가 죽으면 그렇다.
  실패 목록이 `status <> 'SENT'` 인 이유다

## 14. 확인이 필요한 것

- `HARRY_INBOUND_URL` 과 `HARRY_INBOUND_SECRET` 의 실제 값
- 받는 쪽 Vercel 에 환경변수를 넣고 재배포했는지, `curl` 로 201 을 확인했는지
