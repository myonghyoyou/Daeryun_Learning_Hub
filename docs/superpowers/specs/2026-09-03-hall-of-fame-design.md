# 문제 풀이 명예의 전당 — 설계

**작성일:** 2026-09-03
**상태:** 승인됨 (구현 계획 작성 대기)

## 배경

지금 학습 홈에는 랜덤으로 풀기·골라서 풀기·내 풀이 이력 세 카드뿐이다. 자기 기록만 볼 수 있고 남들이 얼마나 푸는지는 알 수 없어, 계속 풀 이유가 개인의 의지 말고는 없다.

기존 통계는 **문제 기준**이다 — 문제별 정답률과 오답 분포를 관리자에게 보여 준다(`lib/stats/statsService.ts`, `lib/db/stats.ts`). **사용자 기준 집계는 없다.**

## 목표

전 사용자의 풀이 기록으로 순위를 매겨 학습 홈에 보여 준다.

## 결정 사항

| 질문 | 결정 | 이유 |
|---|---|---|
| 무엇으로 줄 세우나 | **맞힌 개수** | 많이 풀고 잘 맞혀야 오른다. 정답률만 보면 1문제 맞히고 100%가 되는 구멍이 생긴다 |
| 같은 문제를 여러 번 맞히면 | **맞힐 때마다 센다** | 복습도 점수가 된다 |
| 집계 기간 | **이번 달과 전체 기간 둘 다** | 탭으로 나눈다 |
| 몇 명을 보여주나 | **상위 3개 순위** | 동점은 한 줄로 접는다(아래 참고) |
| 이름 표기 | **이름 + 부서** | "기획팀 홍길동" |
| 대상 | **전 사용자(관리자 포함), 활성 계정만** | 퇴사자가 명예의 전당에 남으면 이상하다 |
| 계산 방식 | **볼 때마다 집계** | 새 표도 마이그레이션도 없다(아래 "규모" 참고) |
| 팀 순위도 매기나 | **매긴다. 팀끼리 경쟁한다** | 개인 순위 아래에 팀 상위 3줄을 함께 둔다 |
| 팀 점수 계산 | **팀원이 맞힌 개수의 합계** | 규칙이 가장 단순하다. 부작용은 아래 참고 |

### 반복 정답을 세는 것의 부작용을 알고 간다

같은 문제를 반복해 맞히면 그만큼 점수가 오르므로, **쉬운 문제 하나를 반복해 순위를 올릴 수 있다.** 이 점을 알고도 복습을 보상하는 쪽을 택했다. 이번 달 순위가 매달 초기화되는 것이 유일한 완화 장치다.

실측(2026-09-03 로컬 개발 DB): 같은 문제를 두 번 이상 맞힌 조합이 이미 1건 있다. 이론상의 이야기가 아니다.

## 순위 규칙

### 공동 순위와 대표

동점은 **같은 순위**를 받고, 순위는 **`DENSE_RANK`** 로 매긴다. 한 줄에 그 무리의 **대표 한 명**과 나머지 인원수를 적는다.

`RANK` 가 아니라 `DENSE_RANK` 인 이유가 있다. 동점을 한 줄로 접으므로 첫 줄이 1위, 둘째 줄이 2위, 셋째 줄이 3위여야 읽힌다. `RANK` 를 쓰면 1위가 5명일 때 다음 줄이 6위가 되어 **1위·6위·9위** 처럼 중간이 빠진 것처럼 보인다.

대신 순위의 뜻이 달라진다는 것을 알고 간다. `DENSE_RANK` 의 "2위"는 "나보다 점수가 높은 사람이 2명"이 아니라 **"두 번째로 높은 점수대"**다. 50명이 1위에 몰려 있어도 그다음은 2위다.

```
1위   기획팀 홍길동  외 2명        12개
2위   영업팀 김철수                 9개
3위   회계팀 이영희  외 4명         7개
```

대표는 그 무리에서 **마지막 정답이 가장 이른 사람**이고, 그것마저 같으면 **사용자 번호가 작은 쪽**이다.

마지막 항(사용자 번호)이 왜 필요한가. 순위는 공동이라 흔들리지 않지만, 그 항이 없으면 **화면에 보이는 대표 이름이 새로고침마다 바뀐다.** 맞힌 개수와 마지막 정답 시각이 모두 같은 두 사람은 실제로 생길 수 있다.

### "상위 3명"은 "줄 세 개"다

1위가 5명이면 그 5명이 한 줄이고, 줄은 최대 세 개다. 사람 수를 3으로 자르지 않는다 — 자르면 동점인데 누구는 나오고 누구는 안 나온다.

`DENSE_RANK` 를 쓰므로 세 줄의 순위는 항상 1위·2위·3위다. 표시되는 사람 수는 동점 상황에 따라 3명일 수도, 수십 명일 수도 있다.

### 내 순위

목록과 **같은 `DENSE_RANK` 값**을 쓴다. 다른 식을 쓰면 같은 사람이 목록에서는 3위, 내 순위에서는 1위로 보인다.

내 순위에도 같은 뜻이 적용된다 — "3위"는 위에 두 사람이 있다는 뜻이 아니라 세 번째 점수대라는 뜻이다. 화면 문구를 "3위"로만 두면 오해할 수 있으므로 **"3위 · 8개"** 처럼 맞힌 개수를 함께 적는다.

본인이 상위 3개 순위 안에 있어도 내 순위 줄은 그대로 둔다. 없으면 "내가 저기 있나"를 눈으로 찾아야 한다.

맞힌 것이 하나도 없으면 내 순위는 없다(`null`). 명단에도 들어가지 않는다.

## 팀 순위

### 팀 점수는 합계다

그 팀 소속 활성 사용자가 맞힌 개수를 모두 더한다. 개인 점수와 같은 규칙을 쓴다 — 같은 문제를 여러 번 맞히면 그만큼 센다.

**사람 많은 팀이 유리하다는 것을 알고 간다.** 1인당 평균으로 나누면 작은 팀도 겨룰 수 있지만, 안 푸는 사람이 많은 팀은 평균이 깎여 개인에게 압박이 간다. 규칙의 단순함을 택했다.

실측(2026-09-03 운영): 팀별 문제 수가 자금팀 30개에서 정보시스템팀 100개까지 벌어져 있다. 인원도 비슷하게 벌어질 가능성이 높으므로 **작은 팀은 상위에 오르기 어렵다**는 점을 기대치로 깔고 본다.

### 순위와 동점

개인과 **같은 규칙**이다 — `DENSE_RANK` 로 매기고, 동점은 한 줄로 접어 대표 팀과 "외 N팀"으로 적는다. 정렬은 합계 내림차순 → 마지막 정답이 이른 팀 → 부서 번호 순이다.

점수가 0인 팀은 명단에 넣지 않는다. 팀이 하나도 없으면 개인과 같은 빈 상태 문구를 쓴다.

### 우리 팀

개인의 "내 순위"와 같은 자리에 **우리 팀의 순위와 합계**를 적는다. 내가 아직 하나도 못 맞혔어도 팀은 점수가 있을 수 있으므로 둘은 따로 계산한다.

## "이번 달"의 경계

`attempts.submitted_at` 은 시간대 없는 컬럼이고 값은 UTC 로 들어간다. 서울 기준 1일 0시로 자르려면 변환해야 한다.

```sql
a.submitted_at >= ((date_trunc('month', now() AT TIME ZONE 'Asia/Seoul')
                    AT TIME ZONE 'Asia/Seoul') AT TIME ZONE 'UTC')
```

**실측 확인(2026-09-03):** 서버 `TimeZone` 이 `Etc/UTC` 인 상태에서 이 식은 `2026-08-31 15:00:00` 을 낸다. 서울 9월 1일 0시를 UTC 로 표현한 값이라 정확하다.

그냥 비교하면 **매달 1일 오전 9시간 동안 지난달 기록이 섞여 들어온다.** 이 저장소가 이미 데었던 자리다(`lib/db/raw.ts` 의 `parseUtcTimestamp`, `vitest.config.ts` 의 `TZ` 고정).

## 화면

### 자리

학습 홈(`/solve`)의 카드 세 개 아래. 2026-09-03 에 걷어낸 추천 문제 세트·학습 루틴 벤토가 있던 자리다.

### 구성

**버튼 묶음 두 개**로 고른다. 축이 서로 다르므로 한 줄에 나란히 둔다.

| 묶음 | 값 | 기본 |
|---|---|---|
| 기간 | 이번 달 / 전체 기간 | 이번 달 |
| 대상 | 개인 / 팀 | 개인 |

고른 조합에 맞는 상위 세 줄을 보여 주고, 그 아래 한 줄을 덧붙인다 — 개인이면 내 순위, 팀이면 우리 팀이다.

**한 축에 네 개를 늘어놓지 않는 이유가 있다.** "이번 달·전체 기간·개인·팀"을 한 줄로 두면 무엇과 무엇이 짝인지 알 수 없다. 두 묶음으로 나누면 각 묶음 안에서 하나만 켜져 지금 무엇을 보고 있는지가 읽힌다.

**세로로 쌓지 않는 이유도 있다.** 개인 세 줄과 팀 세 줄을 함께 보이면 카드가 학습 홈에서 지나치게 길어진다. 대신 개인과 팀을 나란히 견주지는 못한다 — 그 값보다 카드 길이를 택했다.

### 버튼 모양

회색 트랙 위에 고른 쪽만 흰 알약으로 떠오르는 세그먼트 컨트롤이다. 알약 하나가 **미끄러져 이동**한다 — 버튼마다 배경을 켜고 끄면 툭 바뀐다.

알약의 자리와 너비는 버튼을 실제로 재서 넣는다. 글자 길이가 다르기 때문이다("이번 달" 60px vs "전체 기간" 72px, 2026-09-03 실측). 두 칸을 같은 너비로 묶으면 "개인·팀"처럼 짧은 짝에서 빈 공간이 크게 남는다.

### 메달

상위 세 줄에 금·은·동 원반을 붙인다. 원반 안에 1·2·3 을 새기는데, **색만으로는 순서가 안 읽히기 때문이다** — 세 금속은 밝기가 비슷해 색각 이상이 있으면 구분이 어렵다.

원반 위에는 리본 두 가닥이 V 자로 걸린다. 금속 그라데이션이나 반짝임은 넣지 않는다 — 넣어 봤더니 카드가 화려해져 이름과 숫자가 밀렸다.

**메달 상자는 리본까지 품는다**(원반 24px + 드러나는 리본 5px = 29px). 리본을 상자 밖에 두면 가운데 정렬이 원반만 기준으로 맞아, 눈에 보이는 덩어리가 글자보다 2.5px 위로 뜬다 — 정렬은 맞는데 어긋나 보이는 상태가 된다(2026-09-03 실측).

### 움직임

셋 다 짧고 작다. `prefers-reduced-motion` 을 켠 사람에게는 모두 꺼진다.

| 자리 | 움직임 |
|---|---|
| 세그먼트 알약 | 고른 쪽으로 미끄러진다(220ms) |
| 메달 | 나타날 때 작게 시작해 제자리로 튄다(380ms). 금·은·동 80ms 씩 차례로 |
| 순위 줄 | 마우스를 올리면 메달이 살짝 들리며 기운다 |
| 순위표 | 버튼을 눌러 바뀔 때 살짝 올라오며 나타난다(180ms) |

메달의 끝 프레임이 곧 평소 모습이라, 움직임이 끝나도 화면은 그대로다.

### "외 N명" 펼치기

`components/ui` 에 툴팁·팝오버가 없다(2026-09-03 확인: `Modal`·`Collapsible` 만 있다). 범용 툴팁을 새로 만들지 않고 **명예의 전당 안에서만 쓰는 작은 펼침**을 둔다.

- "외 2명"을 버튼으로 만든다
- **마우스를 올리거나, 키보드 포커스가 닿거나, 누르면** 그 줄 아래에 이름 목록이 열린다
- Esc 로 닫는다
- 누르기를 함께 지원하는 이유는 **휴대폰에 마우스 올리기가 없기 때문이다**

팀 목록에서는 단위가 "명"이 아니라 **"팀"**이다("외 2팀").

목록은 **최대 10개**까지 보여 주고 나머지는 "외 N명 더"(팀이면 "외 N팀 더")로 접는다. 아래 "출시 직후" 참고.

### 비어 있을 때

| 상태 | 화면 |
|---|---|
| 맞힌 사람이 없다 | "아직 아무도 문제를 맞히지 않았습니다" 안내 |
| 1~2명뿐이다 | 있는 만큼만 보여 준다. 빈 자리를 만들지 않는다 |
| 내가 맞힌 것이 없다 | 내 순위 줄에 "아직 맞힌 문제가 없습니다" |

### 출시 직후를 대비한다

**2026-09-03 운영 실측: `attempts` 14건, 푼 사람 1명, 활성 사용자 1명.** 계정이 아직 열리지 않았다.

지금 올려도 된다는 결정에 따라 배포하되, 다음을 전제로 만든다.

- 처음에는 명단이 비거나 한 명뿐이다 — 위 표의 빈 상태가 예외가 아니라 기본이다
- 계정이 열리면 한동안 "1문제 맞힘"으로 **수십 명이 동점**일 수 있다. "외 N명"이 예외가 아니라 흔한 모습이므로 10명 상한이 필요하다

## 서버 창구

```
GET /api/solve/hall-of-fame
```

역할 제한 없음. 로그인만 하면 본다.

```
data: {
  month:   { top: [Row], me: Me | null },
  allTime: { top: [Row], me: Me | null }
}

Row = {
  rank: number,                 // 공동 순위(DENSE_RANK). 줄 순서대로 1·2·3
  correctCount: number,
  leader: { userId, name, departmentName },   // 대표
  others: [{ userId, name, departmentName }], // 대표 외 동점자. 최대 10명
  otherCount: number            // 대표 외 전체 인원(10명을 넘어도 실제 수)
}

Me = { rank: number, correctCount: number }
```

`others` 를 10명으로 자르되 `otherCount` 는 실제 수를 담는다. 화면이 "외 12명" 이라 적고 펼치면 10명 + "외 2명 더"를 보여 줄 수 있다.

## 데이터

새 표도 마이그레이션도 없다. `attempts` · `users` · `departments` 만 읽는다.

### 규모

**2026-09-03 운영: `attempts` 14건.** 전 직원 수백 명이 매일 풀어도 연 단위로 수만 건이라, 인덱스 없이도 `GROUP BY` 가 밀리초 단위로 끝난다.

`attempts` 에는 지금 기본키 인덱스뿐이다(2026-09-03 확인). **`attempts` 가 수십만 건을 넘으면** 이번 달 질의를 위해 `submitted_at` 인덱스를 더한다. 전체 기간 질의는 어차피 전 행을 훑으므로 인덱스가 도움이 되지 않는다.

### 부서 상태

부서가 비활성이어도 **순위에서 빼지 않는다.** 팀 목록(`findTeamCounts`)은 부서 상태로 거르지만, 사람의 기록이 부서 상태 때문에 사라지면 안 된다. 두 화면의 규칙이 다른 것은 의도다.

동점을 줄로 접는 일은 **순수 함수로 떼어** 서비스에 둔다. 질의는 사람 한 명당 한 행을 내고, 접는 규칙은 DB 없이 테스트한다.

## 테스트

| 대상 | 방법 |
|---|---|
| 월 경계 — 서울 1일 0시 직전·직후 제출이 갈리는지 | 실제 DB 테스트. `vitest.config.ts` 가 `TZ: "Asia/Seoul"` 로 고정돼 있어 판별력이 생긴다 |
| 맞힌 개수 집계 — 오답·남의 기록·비활성 계정이 섞이지 않는지 | 실제 DB 테스트 |
| 같은 문제를 두 번 맞히면 2로 세는지 | 실제 DB 테스트 |
| 동점이 같은 순위를 받고 다음 줄이 이어지는지(1위·2위·3위, 6위로 건너뛰지 않는다) | 순수 함수 테스트 |
| 대표 선택 — 마지막 정답이 이른 사람, 같으면 사용자 번호가 작은 쪽 | 순수 함수 테스트 |
| 내 순위가 목록의 순위와 같은 값인지 | 서비스 테스트 |
| 상위 3개 순위를 자를 때 동점 무리가 쪼개지지 않는지 | 순수 함수 테스트 |
| `others` 10명 상한과 `otherCount` 실제 수 | 순수 함수 테스트 |
| 맞힌 사람이 0명일 때 빈 응답 | 서비스 테스트 |
| 팀 합계가 팀원 것을 모두 더하는지, 비활성 계정은 빼는지 | 실제 DB 테스트 |
| 팀 동점이 같은 순위를 받고 "외 N팀"으로 접히는지 | 순수 함수 테스트 |
| 우리 팀 순위가 팀 목록의 순위와 같은 값인지 | 서비스 테스트 |
| 내가 0개여도 우리 팀 점수는 나오는지 | 서비스 테스트 |
