# 직군(기술직/행정직)별 문제 분리 설계

## 왜 만드는가

지금 문제를 나누는 축은 **부서 하나뿐**이다. 사용자도 문제도 `department_id` 하나만 보고,
직원용 문제 목록에는 부서 필터조차 없다(`lib/db/solveProblems.ts:47` — Java 파리티 결정).
그래서 로그인한 사람은 **모든 부서의 모든 문제**를 본다.

여기에 기술직 문제은행 500문항(도시가스사업법)이 들어온다. 기존 722문항은 전부 행정직
것이다. 축이 하나뿐인 채로 기술직 문제를 넣으면 이렇게 된다.

- 행정직 직원의 문제 목록에 도시가스사업법 500문항이 섞여 나온다
- 팀 대항 화면의 팀 목록에 `기술직` 칸이 뜬다(`listTeams` 가 전 부서를 돌려준다)
- 명예의 전당이 서로 다른 문제를 푼 사람들을 맞힌 개수만으로 한 줄에 세운다

행정직이 기술직 문제를 풀 이유가 없고 그 반대도 없다. **서로의 직군 문제가 화면에 아예
보이지 않게** 하는 것이 이 작업의 목표다.

## 무엇이 아닌가 — 이건 잠금장치가 아니다

**접근 차단이 아니라 화면 정리다.** 두 직군의 문제은행은 이미 사내 파일서버에 서로 열려
있어 감출 대상이 아니다. 그래서 직군은 사람의 속성으로 저장하지 않고, **로그인할 때 본인이
고른다.** 서버는 그 값이 맞는지 확인하지 않는다.

이 선택의 결과를 분명히 적어 둔다.

- 행정직 직원이 토글을 기술직으로 놓고 들어오면 기술직 문제를 그대로 푼다. **의도된
  동작이다.** 막을 이유가 없다고 판단했다.
- 그래서 `getSolveDetail`·`submitAttempt` 에 직군 검사를 **넣지 않는다.** 잠금장치가 아닌
  것에 `actor` 배선을 서비스와 라우트로 끌고 들어갈 값이 없다. 빠뜨린 게 아니라 뺀 것이다.
- 나중에 진짜로 막아야 할 일이 생기면 그때 `users.track` 을 도입하고 이 두 곳에 검사를
  넣는다. 그 전까지는 하지 않는다.

## 데이터 모델

문제에만 직군을 단다.

```sql
ALTER TABLE problems ADD COLUMN track varchar(20) NOT NULL DEFAULT 'ADMIN'
  CHECK (track IN ('ADMIN', 'TECH'));
```

- `ADMIN` = 행정직, `TECH` = 기술직
- 기본값이 `ADMIN` 이라 **기존 722문항은 손댈 필요가 없다.** 지금 있는 건 전부 행정직이다
- `users` 에는 아무것도 추가하지 않는다

### 왜 부서에 달지 않는가

한 팀 안에 두 직군이 섞인다. 영업팀에는 기술직도 있고 행정직도 있다. 그래서 부서에
직군을 달아 파생시킬 수 없다.

### 왜 사람에게 달지 않는가

직군이 사람의 속성이면 관리자가 계정마다 지정해야 하고(계정 등록 화면·계정 엑셀 업로드·
계정 수정 화면이 전부 바뀐다), 잘못 지정된 계정은 문제를 아예 못 푼다. 막는 것이 목적이
아니므로 그 비용을 낼 이유가 없다.

### 문항번호 유일성은 그대로 둔다

`uq_problems_department_source_number` 는 `(부서, 문항번호)` 를 본다. 기술직 500문항은
새로 만드는 `기술직` 부서에 들어가므로 기존 팀들과 번호가 겹치지 않는다. 제약에 직군을
넣을 필요가 없다.

> 기술직 문제를 기존 부서(예: 공통)에 넣었다면 공통의 1~46번과 정면충돌했을 것이다.
> 전용 부서를 쓰는 이유가 여기에도 있다.

## 직군 선택과 기억

로그인 화면에 행정직/기술직 토글을 둔다. 고른 값은 세션 토큰에 실려 다닌다 —
`departmentId` 가 이미 그렇게 돌아간다(`lib/auth/jwt.ts:31`).

- `AuthUser` 에 `track: "ADMIN" | "TECH"` 추가
- `verifySession` 은 **값이 없으면 `ADMIN` 으로 읽는다.** 배포 전에 발급된 토큰에는 이
  값이 없다. 기존 사용자는 전부 행정직이므로 이 기본값이 정확하고, 강제 로그아웃이 필요 없다
- 세션 동안 직군은 고정이다. 바꾸려면 다시 로그인한다

**기억은 브라우저에 남긴다**(`localStorage`). 다음 로그인 때 토글이 지난번 값으로 미리
잡혀 있다. 사람마다 저장할 필요가 없다고 확인했으므로 DB 컬럼을 만들지 않는다.

> 대가: 다른 PC·브라우저에서는 처음 한 번 다시 골라야 한다. 이게 문제가 되면 `users` 에
> "마지막 선택" 컬럼을 두면 된다 — 접근 규칙이 아니라 편의값이다.

## 거르는 곳

**전부 서버 질의에서 거른다.** 화면에서 거르면 목록 API 가 여전히 남의 직군 문제를 실어
보내고, 화면 하나만 빠뜨려도 새어 나간다.

| 곳 | 함수 | 파일 |
|---|---|---|
| 문제 목록 | `findActiveSolveProblems` | `lib/db/solveProblems.ts` |
| 랜덤 풀이 | `findRandomActiveProblems` | `lib/db/solveProblems.ts` |
| 팀 대항 목록 | `findTeamCounts` | `lib/db/solveTeams.ts:31` |
| 팀 대항 시작 | `findTeamProblemIds` | `lib/db/solveTeams.ts:45` |
| 오답 다시풀기 | `findWrongProblemIds` | `lib/db/solveTeams.ts:61` |
| 팀 목록의 오답 개수 배지 | `countWrongByDepartment` | `lib/db/solveTeams.ts:81` |

각 함수는 `track` 을 인자로 받아 `problems.track = :track` 을 `WHERE` 에 더한다.
호출하는 서비스가 `actor.track` 을 넘긴다.

`findSolveRowsByIds`(`:112`)는 거르지 않는다 — 이미 걸러진 곳에서 나온 id 목록을 받아
본문을 채우는 함수다. 여기서 또 거르면 바퀴 중간의 문제가 조용히 사라진다.

### 팀 목록은 저절로 맞아떨어진다

`findTeamCounts` 에는 이미 `HAVING count(...) > 0` 이 있다. 문제에 직군 조건을 걸면 그
직군의 문제가 없는 부서는 자동으로 빠진다.

- 행정직으로 들어오면 → 기존 13개 팀(`기술직` 부서는 ADMIN 문제가 0개라 빠진다)
- 기술직으로 들어오면 → `기술직` 한 칸(다른 팀은 TECH 문제가 0개라 빠진다)

부서에 직군을 달지 않아도 되는 이유가 이것이다.

### 한 부서에 두 직군이 섞여도 깨지지 않는다

부서를 직군별로 순수하게 유지하도록 **강제하지 않는다.** 관리자가 영업팀에 기술직 문제를
올릴 수 있고, 막을 이유도 없다.

그래서 조건은 전부 `problems.track` 에 건다. 부서가 순수하다고 가정하고 부서 목록으로
거르면, 섞인 부서 하나가 생기는 순간 개수와 목록이 어긋난다. 조건을 문제에 걸면 섞인
부서는 양쪽 목록에 **각각 그 직군 몫의 개수로** 나온다 — 그게 맞는 동작이다.

`countWrongByDepartment` 를 빠뜨리면 이 경우에 배지 숫자만 두 직군 합계로 남는다.

### 주석으로 구분해 둘 것

`lib/db/solveProblems.ts:47` 에는 **"부서 필터를 넣지 마라"** 는 경고가 붙어 있다(Java
파리티 위반). 여기 넣는 것은 부서 필터가 아니라 직군 필터이고 새 업무 규칙이다. 다음
사람이 헷갈리지 않도록 그 구분을 주석에 적는다.

## 명예의 전당

`users.track` 이 없으므로 **푼 문제의 직군으로** 가른다 — `attempts JOIN problems` 후
`problems.track = :actor.track`. `lib/db/hallOfFame.ts:44` 의 개인 순위와 팀 순위 둘 다.

라벨이 아니라 실제로 푼 것으로 재므로 오히려 정확하다. 기술직 500문항과 행정직 722문항은
모수가 달라 맞힌 개수를 그대로 비교할 수 없는데, 이렇게 하면 같은 문제를 푼 사람끼리만
줄을 선다.

- 두 직군을 다 푼 사람은 양쪽 순위에 각각 **그 직군 몫만큼만** 나온다
- 한 팀에 두 직군이 섞여 있으므로 팀 점수도 그 직군 사람들의 몫만 합산된다

## 관리자 화면

| 화면 | 바뀌는 것 |
|---|---|
| 문제 개별 등록·수정 | 직군 선택 추가(필수). 기본값 행정직 |
| 문제 엑셀 일괄 등록 | 직군 선택 추가 — 부서 고르는 자리 바로 옆 |
| 문제 목록(관리자) | 직군 열 표시. 필터는 부서 필터와 같은 방식으로 |
| 관리자 통계·대시보드 | **손대지 않는다.** 관리자는 전체를 봐야 한다 |
| 계정 관련 전부 | **손대지 않는다.** 사람에게 직군이 없다 |

엑셀 업로드의 직군은 **부서와 같이 화면에서 고른다.** 엑셀 파일에 열을 더하지 않는다 —
13번째 컬럼(문항번호)을 뒤에 붙였을 때 겪은 문제를 다시 만들 이유가 없고, 한 파일은
어차피 한 직군이다.

> 부서를 잘못 고른 업로드가 되돌리기 어렵다는 기존 위험이 직군에도 똑같이 붙는다.
> 업로드 결과 화면에 **선택했던 부서와 직군을 같이 보여 준다** — 지금은 성공/실패 건수만
> 나와서 어디로 들어갔는지 알 수가 없다.

## 오류 처리

새로 만드는 오류 문구는 없다.

- 직군 값이 이상하면(토큰 위조 등) `ADMIN` 으로 읽는다. 잠금장치가 아니므로 거절하지 않는다
- 고른 직군에 문제가 하나도 없으면 기존 빈 목록 처리를 그대로 탄다. 팀 대항은 이미
  `NO_PROBLEMS_MESSAGE` 를 가지고 있다
- 이전 직군으로 시작해 둔 팀 대항 바퀴는 남아 있되 **목록에 안 보인다.** 그 부서가 팀
  목록에서 빠지기 때문이다. 그 직군으로 다시 로그인하면 이어서 풀 수 있다. 지우지 않는다

## 시험

| 무엇 | 어떻게 |
|---|---|
| 거르는 함수 6개 | 각 함수에 두 직군 문제를 섞어 넣고 `track` 별로 자기 것만 나오는지 |
| 팀 목록 | 기술직으로 부르면 `기술직` 한 칸, 행정직으로 부르면 기존 팀만 나오는지 |
| 섞인 부서 | 한 부서에 두 직군 문제를 넣고, 양쪽 목록에 각각 제 몫 개수로 나오는지 |
| 명예의 전당 | 두 직군을 다 푼 사람이 양쪽에 각각 그 직군 몫으로만 나오는지 |
| 토큰 하위호환 | `track` 없는 토큰이 `ADMIN` 으로 읽히는지 |
| 로그인 토글 | 고른 값이 세션에 실리는지, 다음 로그인 때 기본값으로 잡히는지 |
| 기존 동작 | 행정직으로 들어왔을 때 지금과 똑같이 보이는지(회귀) |

기존 시험이 `track` 컬럼 추가로 깨지는지 함께 본다 — 기본값이 `ADMIN` 이라 대부분 그대로
지나가야 한다.

## 적재 순서

1. 마이그레이션 배포(`problems.track` 추가) — 기존 문제는 전부 `ADMIN` 이 된다
2. 관리자 화면에서 부서 `기술직`(코드 `TECH`) 생성
3. 문제 엑셀 일괄 등록 → 부서 `기술직`, 직군 `기술직` 선택 → `문제_기술직.xlsx`(428행)
   업로드. **성공 428 / 실패 0** 확인
4. `_미업로드_빈칸_수동입력.xlsx` 의 72문항을 개별 등록 화면에서 입력(직군 기술직)
5. 기술직으로 로그인해 문제 목록·랜덤·팀 대항에 도시가스사업법 문제만 나오는지,
   행정직으로 로그인해 지금과 똑같은지 확인

산출물과 업로드 절차는 `docs/문제은행_엑셀_기술직/README.md` 에 있다.

## 안 하는 것

- `users.track` — 사람에게 직군을 달지 않는다(위 "무엇이 아닌가")
- `departments.track` — 한 팀에 두 직군이 섞이므로 성립하지 않는다
- `getSolveDetail`·`submitAttempt` 의 직군 검사 — 잠금장치가 아니다
- 엑셀 파일의 직군 열 — 화면에서 고른다
- 계정 화면·관리자 통계 — 바뀌지 않는다
- 기술직 문제의 팀 분할 — 기술직 문제은행은 한 과목 통번 1~500이라 팀이 없다.
  나중에 나눌 일이 생기면 부서를 더 만들면 된다(이 설계는 그걸 막지 않는다)
