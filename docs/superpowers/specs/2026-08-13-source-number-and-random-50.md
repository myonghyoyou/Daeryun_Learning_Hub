# 출처 번호 표기와 랜덤 50문제 — 합의 사항

- 작성일: 2026-08-13
- 상태: **결정 완료, 구현 계획 미작성**
- 근거: 2026-08-13 grilling 세션
- 원본 요청: "랜덤으로 풀기에 문제 수가 50개가 되어 있으면 좋을 것 같고, 문제를 풀 때 해당 문제가 어느 영역의 몇 번에 있는 문제인지를 표기해야 할 듯하다"

이 문서는 **무엇을 만들지에 대한 합의**만 담는다. 어떻게 만들지는 별도 계획서에서 다룬다.

## 1. 요청 두 가지

| # | 요청 | 결론 |
|---|---|---|
| 1 | 랜덤 풀이에 50문제 선택지 | 화면 상수 한 줄. 백엔드 상한이 이미 50이다 |
| 2 | 풀 때 "어느 영역의 몇 번" 표기 | **영역 = 기존 부서**로 밝혀져 컬럼 하나만 추가하면 된다 |

## 2. 조사로 확정한 사실

grilling 중 코드와 자료를 뒤져 확인한 것들이다. 추측이 아니다.

### 2.1 랜덤 50은 백엔드가 이미 지원한다

`SolveServiceImpl.MAX_RANDOM_COUNT = 50` 이고 `randomSet()` 은 1~50을 받는다. 화면 `RandomSetupPage.COUNT_OPTIONS` 가 `5 / 10 / 20` 만 제공할 뿐이다. **백엔드 변경 없음.**

### 2.2 영역·번호를 담을 자리가 없다

`problems` 테이블: `type, content, image_url, reference_text, explanation, blank_reveal_count, status, department_id, created_by, created_at, updated_at`. 영역·번호에 해당하는 컬럼이 없다.

엑셀 업로드도 12개 고정 컬럼(`유형 / 내용 / 이미지 / 참조 / 보기1~5 / 정답 / 해설 / 태그`)뿐이다.

Plan 4가 이 부재를 이미 만났고 "과목·단원·난이도는 데이터 모델에 없어 다루지 않는다"(결정 G5)로 보류한 이력이 있다.

### 2.3 출처 문서의 실제 구조

`docs/★2025 문제은행(행정직) - 배포용.hwp` 의 미리보기를 추출해 확인했다(본문 스트림은 배포용 보호가 걸려 있다):

```
<문 제 은 행>   <행정직>   2025년 12월

▣ 공통문제
1. 도시가스사업법의 목적을 달성하기 위한 방법으로 맞는 것은?
   ① … ② … ③ … ④ …
2. 가스사용자의 시설이라 함은 …
```

**구획(▣)과 그 안의 일련번호가 실제로 존재한다.** 요청의 "영역"과 "번호"가 이것이다.

### 2.4 변환 작업이 이미 되어 있다

`docs/문제은행_엑셀/` (git 미추적)에 2026-08-09자 변환 결과가 있다.

| 항목 | 값 |
|---|---|
| 원본 | PDF 44쪽, **12개 그룹, 722문항** |
| 엑셀 업로드용 | 팀별 파일 12개, **653행** |
| 수동 입력 필요 | **69문항** (다중빈칸 50 · 보기추출 실패 8 · 파싱 실패 11) |

그룹 = 팀이다: 공통 · 기획팀 · 업무지원팀 · 회계팀 · 자금팀 · 총무1팀 · 고객지원팀 · 수입관리팀 · 인사팀 · 정보시스템팀 · 영업팀 · 공사관리팀.

> 사용자가 구두로 든 "공통·정보시스템·기획·회계·자금 등"의 **"등"이 7개 팀을 더 포함**한다. 실제는 12개다.

### 2.5 학습자용 DTO 세 개 모두 부서 정보를 갖고 있지 않다

| DTO | 필드 |
|---|---|
| `ProblemSolveDetailResponse` | id, type, content, imageUrl, referenceText, choices, blanksToAnswer, revealedBlanks |
| `ProblemSolveListItem` | id, type, content, tags |
| `AttemptHistoryItem` | problemId, problemContent, submittedAnswer, correct, submittedAt |

표기를 넣으려면 세 DTO와 각 SQL에 부서명·번호를 더해야 한다. **작업량이 "컬럼 하나 추가"보다 크다.**

### 2.6 문제의 부서를 바꾸는 API가 이미 있다

`ProblemController` 의 부서 변경 엔드포인트(`DepartmentChangeRequest`). 번호에 부서 단위 유일성을 걸면 이 경로가 충돌한다.

### 2.7 현재 부서는 실제 팀이 아니다

`본사(HQ) · 개발팀(DEV) · 영업팀(SALES) · 폐지팀(OLD, 비활성)`. 12개 실팀과 다르다. 테스트 데이터로 보인다.

## 3. 결정 사항

### D1. 영역은 새 개념이 아니라 **기존 부서**다

`source_section` 같은 컬럼을 만들지 않는다. 부서(`department_id`)가 곧 영역이다.

- `problems` 에 **`source_number INT` 하나만** 추가
- 표기는 기존 부서명을 그대로 쓴다
- 부서 마스터 정리(본사·개발팀·영업팀 → 12개 실팀)는 **사용자가 관리 화면에서 직접** 한다. 구현과 독립적이라 순서는 자유다

> 초기에는 "부서·태그와 독립적인 출처 좌표"로 정했다가, 영역이 팀 이름이라는 사실이 나온 뒤 뒤집었다. 같은 개념을 두 벌로 관리하지 않기 위해서다.

### D2. 번호는 등록·수정 모두 **필수**

생성과 수정에 같은 규칙을 적용한다. 규칙이 하나여서 예외를 기억할 필요가 없다.

### D3. 번호 기본값은 **그 부서의 마지막 번호 + 1**

부서를 고르면 자동으로 채워진다. 첫 문제면 1. 손으로 바꿀 수 있다.

### D4. 같은 부서에 같은 번호는 **거부**

`UNIQUE(department_id, source_number)`.

### D5. 번호는 **재사용하지 않는다**

보관된 문제도 번호를 점유한다. `자금 12번`을 보관하면 12번은 영구히 비고 다음 문제는 13번을 받는다. 종이 문제집에서 문항을 뺀 것과 같은 모양이다.

> 사용자 확인: "어차피 문제 테이블 데이터를 싹 밀고 부서와 문제 번호를 새로 넣을 것이므로 괜찮다."

### D6. 부서를 옮기면 **새 부서의 마지막+1로 자동 재부여**

바뀐 번호를 화면에 알린다. 등록할 때와 같은 규칙이라 일관된다.

### D7. 엑셀은 **맨 뒤에 번호 컬럼 1개 추가**, 필수

13번째 컬럼(0-기준 index 12). 파일 내 중복과 DB 중복 모두 행 단위로 거부한다.

**중간에 끼우지 않는 이유**: 기존 파일의 정답·해설이 한 칸씩 밀려 **조용히 잘못 읽힌다.** 뒤에 붙이면 예전 파일이 "번호는 필수입니다"로 행마다 뚜렷이 실패한다.

> 이 결정의 무게는 §2.4 때문에 커진다. 653행을 올릴 때 번호가 엑셀에 들어 있지 않으면 손으로 653번 입력해야 한다.

### D8. 표기는 **유형 배지 옆 회색 배지**

```
[객관식(단일)] [정보시스템 3번]
```

유형은 파란 계열(info), 출처는 회색(ink-muted). 무엇이 문제의 성격이고 무엇이 위치 정보인지 한눈에 갈린다.

### D9. 표기 범위는 **학습자 경로 전체**

풀이 화면 · 문제 목록 · 풀이 이력 · 랜덤 결과 요약. 관리자 화면은 입력만 하고 표시는 지금 그대로 둔다.

### D10. 문제 수 선택지는 `5 / 10 / 20 / 50`

문제가 요청보다 적으면 지금처럼 있는 만큼 시작한다. 진행 표시가 `1 / 12` 로 나오므로 별도 안내를 넣지 않는다.

## 4. 이번 범위 밖

- **부서 마스터 정리** — 사용자가 직접 (D1)
- **영역·번호로 검색·필터·정렬** — 표기 전용으로 정했다
- **랜덤 풀이를 영역으로 좁히기** — 부서 필터가 이미 그 역할을 한다
- **관리자 화면(문제 목록·통계)에 번호 표시**
- **722문항 실제 적재** — 데이터 작업이지 기능 개발이 아니다

## 5. 계획서가 풀어야 할 문제

결정은 끝났지만, 구현 계획을 쓸 때 답해야 할 것들이 남아 있다.

1. **`source_number` 를 NOT NULL 로 걸 수 있는가.** 기존 14건에 값이 없다. "싹 밀고 새로 넣는다"면 밀어낸 뒤 NOT NULL 이 가능하지만, 그 순서를 계획이 명시해야 한다.
2. **마지막+1 을 어디서 계산하는가.** 화면이 조회 API 를 부르는가, 서버가 빈 값을 채우는가. 동시에 두 명이 등록하면 같은 번호를 받는다 — `UNIQUE` 가 막아 주지만 그때 화면이 무엇을 보여줄지 정해야 한다.
3. ~~엑셀 업로드는 부서를 엑셀에서 못 받는다.~~ **해소된 문제다.** `docs/문제은행_엑셀/README.md`(2026-08-09) 가 "로그인한 관리자의 부서로 귀속된다"고 경고하지만, 그 뒤 `2026-08-09-excel-upload-department-selection` 계획이 **업로드마다 귀속 부서를 고르는 기능**을 넣었다(`uploadExcel(file, departmentId, actor)` + 화면의 "귀속 부서" Select). 총괄 관리자 계정 하나로 12개 파일을 부서만 바꿔 가며 올릴 수 있다. **팀별 관리자 계정 12개는 필요 없다.**
4. **`ProblemSolveListItem` 에 부서명을 넣으면** 학습자 문제 목록이 처음으로 부서를 노출한다. 지금은 유형·내용·태그만 보인다.
5. **다중빈칸 50문항은 엑셀로 못 올린다**(§2.4). 개별 등록 화면으로 넣어야 하고, 그 화면에도 번호 입력이 필요하다.
