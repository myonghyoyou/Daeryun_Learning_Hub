## 1. 조사로 확정한 사실

추측이 아니라 코드와 공식 문서를 뒤져 확인한 것들이다.

### 1.1 Vercel 은 이 백엔드를 호스팅하지 못한다

Spring Boot 2.7.3 / Java 8 이다. Vercel 의 서버리스 런타임은 JVM 을 돌리지 않는다.
**프론트엔드와 백엔드는 어차피 갈라진다.**

### 1.2 백엔드 규모 — Next 재작성은 재작성이지 마이그레이션이 아니다

| 대상 | 규모 |
|---|---|
| 본체 | 134파일 / **5,303줄** (서비스 로직만 2,991줄) |
| 엔드포인트 | 31개 |
| SQL 문 | 매퍼 14개에 62문 |
| 테스트 | 38파일 / **7,304줄 — 301개** |

합계 약 **12,600줄**. 옮기기 까다로운 지점이 몰려 있다.

- `REQUIRES_NEW` **12곳** — 엑셀 653행 중 한 행이 실패해도 다음 행이 사는 근거다. Node 엔
  선언적 트랜잭션 전파가 없어 커넥션을 손으로 들고 다녀야 한다
- POI 엑셀 파싱 — 셀 타입 처리가 달라 검증 규칙을 다시 맞춰야 한다
- 인증·잠금 26곳 — 세션, 5회 실패 잠금, BCrypt, 비밀번호 변경 강제
- 중복 번호를 한국어로 바꾸는 로직은 Spring 의 MyBatis 예외 변환(SQLState 23505 →
  `DuplicateKeyException`)에 기대고 있다. `pg` 드라이버에선 `err.code` 를 직접 봐야 한다

> **그리고 Next 로 옮겨도 배포의 진짜 문제 두 개가 그대로 남는다.** 서버리스는 상태가 없고
> 파일시스템이 임시라, 세션 저장소와 오브젝트 스토리지가 여전히 필요하다. Next 가 없애 주는
> 건 "호스트가 두 개"라는 문제 하나뿐인데 그건 rewrites 설정 몇 줄로 해결된다.

### 1.3 리전 — 한국에서 쓸 때 실제로 갈린다

| | 서울 | 도쿄 | 싱가포르 |
|---|---|---|---|
| Supabase | ✅ ap-northeast-2 | ✅ | ✅ |
| Neon | ❌ (리전 8곳) | ❌ (요청 단계) | 확인 필요 |
| Fly.io | ❌ (요청만 올라와 있음) | ✅ nrt | ✅ |
| Railway | ❌ | ❌ | ✅ |
| Render | ❌ | ❌ 개발 중 | ✅ |

MyBatis 앱은 요청당 DB 왕복이 여러 번이라 **백엔드와 DB 는 같은 리전에 둔다.**

### 1.4 메일이 계정 생성을 막는다 — 배포 블로커였다

`AccountProvisioningServiceImpl.provision()` 과 `UserAdminServiceImpl.create()` 가
`mailService.sendTemporaryPassword(...)` 를 호출한다. `mailSender.send()` 는 실패 시
unchecked 예외를 던지고, 두 메서드 모두 트랜잭션 안이라 **메일이 실패하면 계정 생성이
롤백된다.** 의도된 설계이며 javadoc 에 그렇게 적혀 있다.

운영 기본값은 `MAIL_HOST=localhost:25` 다. 그대로 올리면 **계정을 하나도 만들 수 없다.**
지금 개발에서 되는 것은 MailHog 가 따로 떠 있기 때문이고 `docker-compose.yml` 에는 없다.

비밀번호 초기화 경로는 없다 — 임시 비밀번호가 생기는 곳은 **개별 등록과 엑셀 일괄 등록
두 곳뿐**이다.

### 1.5 이미지 기능은 쓰이지 않고 있다

`SELECT count(*) FILTER (WHERE image_url IS NOT NULL) FROM problems` → **26건 중 0건**.
`backend/uploads/images/` 의 파일 2개는 70바이트짜리 테스트 산출물이다.

### 1.6 세션은 메모리에 있다

`HttpSession` 을 쓰고 Spring Session 의존성이 없다. 타임아웃 90분, `SameSite=Lax`,
`secure` 는 `SESSION_COOKIE_SECURE` 로 전환한다. **재시작하면 전원 로그아웃된다** —
QA 중 백엔드를 재기동할 때마다 실제로 겪었다.

### 1.7 부트스트랩 러너

`SuperAdminBootstrapRunner` 는 총괄 관리자가 **없을 때만** 실행되고
`mustChangePassword=true` 로 만든다. 함께 `본사(HQ)` 부서를 하나 만든다.
기본 비밀번호가 `changeme1234` 이므로 **`BOOTSTRAP_ADMIN_PASSWORD` 를 반드시 설정한다.**

### 1.8 스키마

`spring.sql.init.mode: always` 라 부팅마다 `schema.sql` 이 돈다. 전부
`CREATE TABLE IF NOT EXISTS` 여서 기존 DB 에는 no-op 이고, 컬럼 추가는 별도 마이그레이션
스크립트가 담당한다(`backend/db/migration/`).

## 2. 결정 사항

### D1. Spring Boot 를 유지하고 Vercel 은 프록시로 쓴다

프론트는 Vercel, 백엔드는 별도 호스팅. `vercel.json` 의 rewrites 로 `/api` 와 `/uploads`
를 백엔드로 넘긴다. **브라우저는 Vercel 도메인만 본다.**

- 세션 쿠키가 1st-party 로 유지돼 `SameSite=Lax` 를 그대로 쓴다
- CORS 설정이 필요 없다
- 301개 테스트가 그대로 살아 있는다

> Next 전환은 "배포 때문에"가 아니라 "한 언어로 통일한다"는 별도 이유가 섰을 때, 배포가
> 안정된 뒤에 판단한다. 지금 하면 배포 문제와 재작성 버그를 동시에 상대하게 된다.
> 다만 Java 8 / Spring Boot 2.7 은 이미 EOL 이라 **어느 쪽을 고르든 언젠가는 손봐야 한다.**

### D2. 단일 인스턴스로 간다. 배포 시 로그아웃은 감수한다

사내 용도이고 교육 시즌에 몰리는 버스티한 사용이다. 그 결과 **백엔드 코드 수정이 거의
없어진다** — 세션은 메모리 그대로, Spring Session 의존성도 테이블도 필요 없다.

제약이 하나 따라온다. **인스턴스가 잠들면 안 된다.** 슬립·스케일투제로가 곧 전원
로그아웃이다. Render 무료 티어(15분 유휴 시 중단)가 이 조건에서 탈락한다.

### D3. 백엔드는 Railway 싱가포르

설정이 가장 쉽다. 도쿄를 쓸 수 있는 Fly.io 가 지연 면에서 유리하지만, 운영 편의를 택했다.

### D4. DB 는 Supabase 싱가포르

백엔드와 같은 리전. 관리형 Postgres 로서 성숙해 백업·복구·SQL 에디터가 갖춰져 있고,
722문항 적재나 백필 같은 작업에 손이 편하다. Neon 은 아시아 리전이 약해 앞으로 더 가까운
곳으로 옮길 여지가 없다.

> 무료 티어는 1주일 유휴 시 프로젝트가 일시중지된다. 시즌형 사용이라 **유료 전환이 사실상
> 필수**다.

### D5. 이미지는 Railway 볼륨

볼륨을 마운트하고 `UPLOAD_IMAGE_DIR` 만 그 경로로 바꾼다. **백엔드 코드 수정 0줄.**
쓰이지도 않는 기능(§1.5) 때문에 배포 직전에 코드를 건드리지 않는다.

오브젝트 스토리지 이전은 다중 인스턴스가 필요해질 때 다시 판단한다.

### D6. 메일을 걷어내고 임시 비밀번호를 화면에 표시한다

외부 의존성이 사라져 배포가 막히지 않는다. 매년 한 번 직원을 등록하는 사내 도구에는
오히려 현실적이다.

- 개별 등록: 생성 직후 화면에 임시 비밀번호를 보여 준다
- 임시 비밀번호는 **감사 로그에 남기지 않는다**(현재 `buildCreateDetail` 은 사번만 담는다 —
  이 성질을 유지한다)

### D7. 일괄 등록은 결과 표에 표시하고 엑셀로도 내려받는다

지금 행별 오류를 보여 주는 결과 화면에 성공 행의 임시 비밀번호를 함께 넣고, 한 번에 받을
수 있게 파일로 내려받는다. 200명을 올려도 관리자가 베끼는 사고가 없다.

> 구현 노트: 응답에 이미 담긴 값으로 프론트에서 파일을 만든다. 서버는 해시만 갖고 있어
> 나중에 다시 만들어 줄 수 없다. 한글이 깨지지 않도록 **UTF-8 BOM** 을 붙인다.

### D8. 운영 DB 는 빈 상태에서 시작한다

개발 DB 는 건드리지 않는다. 부트스트랩이 총괄 관리자와 `본사(HQ)` 를 만들면 거기서
시작해 12개 팀을 만들고 722문항을 올린다.

QA 중 만든 문제 11건·랜덤 완주 기록·테스트 계정이 운영 통계에 섞이지 않는다.
spec `2026-08-13-source-number-and-random-50.md` D5 의 "어차피 싹 밀고 새로 넣는다"와도 맞는다.

## 5. 아직 정하지 않은 것

grilling 을 이어서 결정해야 한다.

1. **도메인** — `*.vercel.app` 서브도메인으로 갈지 사내 커스텀 도메인을 붙일지.
   `SESSION_COOKIE_SECURE` 와 쿠키 설정이 여기에 딸린다
2. **빌드 방식** — Railway 의 Nixpacks 자동 감지에 맡길지 Dockerfile 로 못 박을지.
   Java 버전을 고정할지도 함께 정한다
3. **스키마 적용 절차** — `schema.sql` 자동 실행에 맡길지, 마이그레이션 스크립트를 먼저
   손으로 적용할지. `source_number` 마이그레이션이 이미 하나 있다
4. **시크릿 목록과 주입 방법** — `BOOTSTRAP_ADMIN_PASSWORD`, DB 접속 정보,
   `SESSION_COOKIE_SECURE`, `CORS_ALLOWED_ORIGINS`
5. **722문항 적재 시점** — 배포 직후인지 직원 공개 전인지
6. **확인이 필요한 제약** — Vercel rewrites 의 요청 본문 크기 제한이 엑셀 업로드(최대
   20MB 설정)와 이미지 업로드(최대 5MB)에 걸리는지
7. **Supabase 접속 방식** — 직결과 풀러(pgBouncer) 중 무엇을 쓸지. 단일 인스턴스 +
   HikariCP 라 직결이 유력하다
