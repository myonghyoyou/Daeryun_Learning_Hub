# 골라서 풀기를 팀 단위 풀이로 바꾸기 — 설계

**작성일:** 2026-09-02
**상태:** 승인됨 (구현 계획 작성 대기)

## 배경

지금 "골라서 풀기"(`/solve/problems`)는 문제 목록을 보여 주고 하나를 눌러 그 문제 하나만 푸는 화면이다. 직원이 자기 팀 문제를 처음부터 끝까지 훑는 길이 없다.

한편 "랜덤으로 풀기"는 이미 여러 문제를 이어서 푸는 장치를 갖추고 있다 — 문제를 하나씩 보여 주고, 채점 결과를 확인할 시간을 준 뒤 "다음 문제"로 넘기고, 마지막에 결과를 요약한다. 다만 진행 상태를 브라우저 탭 안(`sessionStorage`)에만 두어 탭을 닫으면 사라진다.

## 목표

"골라서 풀기"를 **한 팀의 문제를 처음부터 끝까지 푸는 흐름**으로 바꾼다. 한 팀이 30~100문제라 한 자리에서 다 풀기 어려우므로, 멈춘 자리에서 이어 풀 수 있어야 한다.

## 결정 사항

| 질문 | 결정 | 이유 |
|---|---|---|
| 검색·태그는? | **없앤다.** 팀만 고른다 | 화면이 한 가지 일만 한다. 문제 하나를 찾아 푸는 길은 사라진다 |
| 중간에 나갔다 오면? | **멈췄던 데부터** | 100문제를 매번 처음부터 다시 풀 수는 없다 |
| 문제 순서는? | **문제집 번호 오름차순** | 순서가 항상 같아야 이어 풀기가 성립한다. 직원이 종이 문제집과 대조하기도 좋다 |
| 다 푼 뒤 다시 누르면? | **두 갈래 중 선택** — 처음부터 다시 / 이전에 틀린 문제만 | 실수로 진행이 날아가지 않고, 복습 경로가 생긴다 |
| "틀린 문제"의 범위는? | **문제마다 가장 마지막에 낸 답이 오답인 것** | 예전에 틀렸어도 나중에 맞혔으면 뺀다 — 지금 모르는 문제만 남는다 |
| 진행 상태를 어디에 두나? | **서버 테이블 한 개** | 아래 "저장 구조 선택" 참고 |

### 저장 구조 선택

| 방식 | 판단 |
|---|---|
| **바퀴 하나를 한 행으로 남기는 테이블** | **채택.** 이어 풀기·다시 풀기·틀린 것만 세 갈래가 모두 같은 구조로 풀린다 |
| 새 테이블 없이 풀이 이력에서 계산 | 첫 바퀴는 되지만 **다시 풀기 바퀴에서 위치를 알 수 없다.** 이미 모든 문제에 답한 상태라 "아직 안 푼 첫 문제"라는 계산이 무너진다 |
| 지금처럼 브라우저에만 | 탭을 닫으면 처음부터다. "멈췄던 데부터"라는 결정과 어긋난다 |

이 문서에서 **"바퀴"**는 한 팀을 한 번 훑는 단위를 뜻한다. 같은 팀을 두 번 풀면 바퀴가 둘이다.

## 화면 흐름

### 팀 목록 (`/solve/problems`)

팀마다 한 줄이다. 팀 이름, 정상 문제 수, 내 상태를 보여 준다.

| 내 상태 | 표시 | 눌렀을 때 |
|---|---|---|
| 진행 중인 바퀴가 있다 | `12 / 30 진행 중` | 진행 화면으로, 멈췄던 문제부터 |
| 끝난 바퀴만 있다 | `틀린 문제 8개` | **선택 화면**으로 |
| 바퀴가 하나도 없다 | `아직 안 풂` | 새 바퀴(전체)를 만들고 진행 화면으로 |

**마지막 바퀴의 성적이 아니라 지금 틀린 문제 수를 적는 이유**가 있다.

"다 풀었음"은 사실과 다를 수 있다 — 중간에 그만둔 바퀴도 끝난 바퀴다. 그렇다고 마지막 바퀴의 성적(`22 / 30 정답`)을 적으면 **복습 바퀴를 막 끝낸 팀에서 무너진다.** 8문제짜리 복습 바퀴가 마지막이면 `5 / 8` 이 되어, 팀 전체가 30문제인데 분모가 8로 보인다. 무슨 숫자인지 알 수 없다.

틀린 문제 수는 어느 바퀴를 마지막에 돌았든 뜻이 같고, 복습 버튼을 누르면 나올 개수와 정확히 일치한다.

문제가 0개인 팀은 목록에 보이되 누를 수 없다.

### 선택 화면 (`/solve/problems/[departmentId]`)

버튼 두 개다.

- **처음부터 다시 풀기** — 그 팀의 정상 문제 전부로 새 바퀴를 만든다
- **이전에 틀린 문제 다시 풀어보기** — 마지막 답이 오답인 문제만으로 새 바퀴를 만든다

틀린 문제가 하나도 없으면 두 번째 버튼은 "틀린 문제가 없습니다"로 비활성화한다.

이 주소로 직접 들어왔는데 진행 중인 바퀴가 있으면 진행 화면으로 돌려보낸다 — 두 바퀴가 동시에 열리지 않게 한다.

### 진행 화면 (`/solve/problems/[departmentId]/play`)

랜덤 풀기와 같은 문제 카드를 쓴다. 문제 하나를 보여 주고, 답을 내면 채점 결과를 보여 주고, "다음 문제"를 눌러야 넘어간다. 위쪽에 `12 / 30` 진행 표시를 둔다.

"여기서 그만두고 결과 보기" 탈출구를 둔다 — 문제 불러오기가 계속 실패할 때의 출구다.

### 결과 화면 (`/solve/problems/[departmentId]/result?run=<바퀴 id>`)

**답을 낸 개수 중 맞은 개수**(건너뛴 문제는 양쪽 모두에서 뺀다)와 틀린 문제 목록을 보여 주고, 선택 화면과 같은 버튼 두 개를 둔다. `run` 이 없으면 그 팀의 가장 최근 끝난 바퀴를 보여 준다.

### 복습 바퀴를 끝낸 뒤

전체 바퀴든 복습 바퀴든 끝나면 **같은 결과 화면, 같은 버튼 두 개**로 간다. 복습 바퀴 뒤에만 다른 화면을 두지 않는다.

다만 "이전에 틀린 문제"는 **방금 낸 답까지 반영해 매번 다시 계산한다.** 8문제를 복습해 5개를 맞혔다면 다음 복습 대상은 남은 3개다. 3개까지 맞히면 대상이 0개가 되어 복습 버튼이 비활성화되고, "처음부터 다시 풀기"만 남는다.

별도 규칙 없이 **틀린 문제가 없어질 때까지 좁혀지는 복습 고리**가 된다. "문제마다 가장 마지막에 낸 답을 본다"는 규칙 하나에서 저절로 따라 나오는 동작이다.

## 문제 순서 규칙

한 팀의 바퀴에 담을 문제를 고르고 줄 세우는 규칙이다.

1. 그 부서 소속이면서 **정상(ACTIVE)** 인 문제만
2. `source_number` 오름차순, **번호가 비어 있으면 맨 뒤**
3. 번호가 같으면 `id` 오름차순

2·3번이 함께 있어야 순서가 한 가지로 정해진다. 번호가 비어 있거나 겹치는 문제가 있어도 매번 같은 줄이 나온다.

## "틀린 문제" 정의

문제마다 그 사용자가 낸 답 중 **가장 나중 것 하나**를 골라, 그것이 오답인 문제만 모은다. 대상은 그 팀의 정상 문제로 한정하고, 줄 세우는 규칙은 위와 같다.

같은 시각에 제출된 답이 둘일 경우 `attempts.id` 가 큰 쪽을 나중 것으로 본다.

## 저장 구조

`solve_runs` 테이블을 새로 만든다.

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `id` | bigserial PK | |
| `user_id` | bigint NOT NULL → `users.id` | 누구의 바퀴인지 |
| `department_id` | bigint NOT NULL → `departments.id` | 어느 팀인지 |
| `mode` | varchar(10) NOT NULL | `ALL` 또는 `WRONG` |
| `problem_ids` | jsonb NOT NULL | 시작할 때 확정한 문제 id 배열(줄 세운 순서 그대로) |
| `cursor` | integer NOT NULL DEFAULT 0 | 지금 몇 번째인지(0부터) |
| `results` | jsonb NOT NULL DEFAULT `'[]'` | `[{ problemId, correct }]` — 넘어갈 때마다 하나씩 쌓인다 |
| `status` | varchar(20) NOT NULL DEFAULT `'IN_PROGRESS'` | `IN_PROGRESS` 또는 `FINISHED` |
| `created_at` | timestamp NOT NULL DEFAULT now() | |
| `updated_at` | timestamp NOT NULL DEFAULT now() | |

제약:

- `mode`·`status` 는 CHECK 로 값을 묶는다 (기존 테이블들과 같은 방식)
- **한 사람이 한 팀에 대해 진행 중인 바퀴는 최대 하나** — 부분 유니크 인덱스로 막는다
  ```sql
  CREATE UNIQUE INDEX solve_runs_one_active
    ON solve_runs (user_id, department_id) WHERE status = 'IN_PROGRESS';
  ```
  두 탭에서 동시에 시작해도 바퀴가 둘로 갈라지지 않는다.

**문제 목록을 시작 시점에 박아 두는 이유.** 그러지 않으면 푸는 도중 관리자가 문제를 추가하거나 보관 처리했을 때 총 개수와 순서가 발밑에서 바뀐다. `12 / 30` 이 갑자기 `12 / 31` 이 되는 일을 막는다.

**결과를 바퀴 행에 쌓는 이유.** 채점 결과는 `attempts` 에도 남지만, 거기에는 어느 바퀴에서 낸 답인지가 없다. 다른 탭에서 같은 문제를 병행해 풀면 시각만으로는 갈라낼 수 없다. `attempts` 를 건드리지 않고 정확한 요약을 내기 위해 바퀴 행에 따로 쌓는다.

## 서버 창구

응답 봉투는 기존과 같다 — `{ resultCode, resultMsg, data }`.

### `GET /api/solve/teams`

팀 목록과 내 진행 상태.

```
data: [{ departmentId, departmentName, totalCount,
         activeRun: null | { runId, mode, cursor, total },
         hasFinishedRun: boolean,
         wrongCount }]
```

- `activeRun` — 진행 중인 바퀴. 없으면 `null`
- `hasFinishedRun` — 끝난 바퀴가 하나라도 있는지. 목록의 세 갈래 중 `아직 안 풂` 과 `틀린 문제 N개` 를 가른다
- `wrongCount` — **지금** 마지막 답이 오답인 문제 수(그 팀 정상 문제 대상). 목록 표시와 복습 버튼 활성화가 같은 값을 쓴다

### `POST /api/solve/teams/{departmentId}/runs`

새 바퀴를 만든다. 본문은 `{ mode: "ALL" | "WRONG" }`.

- 진행 중인 바퀴가 이미 있으면 **새로 만들지 않고 그 바퀴를 그대로 돌려준다.** 두 탭에서 동시에 눌러도 유니크 인덱스 충돌이 사용자에게 오류로 보이지 않는다.
- 담을 문제가 0개면 `resultCode` 로 거절한다(빈 바퀴를 만들지 않는다).

```
data: { runId, mode, cursor, total, status, problems: [{ id, type, content, departmentName, sourceNumber }] }
```

### `POST /api/solve/runs/{runId}/advance`

한 문제 넘어간다. 본문은 `{ fromCursor, correct }`.

- `fromCursor` 가 지금 `cursor` 와 다르면 아무것도 하지 않고 지금 상태를 돌려준다. 새로고침 뒤 "다음 문제"를 두 번 눌러 두 칸 건너뛰는 일을 막는다.
- `results` 에 `{ problemId, correct }` 를 하나 쌓고 `cursor` 를 1 늘린다.
- `correct` 는 `true`·`false`·`null` 세 가지다. **`null` 은 건너뛴 문제**다(문제가 그사이 보관 처리돼 불러오지 못한 경우). 맞은 것으로도 틀린 것으로도 세지 않는다.
- `cursor` 가 마지막에 닿으면 `status` 를 `FINISHED` 로 바꾼다.
- 자기 바퀴가 아니면 거절한다.

```
data: { cursor, status, total }
```

### `POST /api/solve/runs/{runId}/finish`

바퀴를 지금까지 푼 만큼만 남기고 끝낸다. 진행 화면의 "여기서 그만두고 결과 보기"가 쓴다.

`status` 를 `FINISHED` 로 바꾸는 것이 전부다 — `cursor` 와 `results` 는 손대지 않는다. 이 창구가 없으면 중간에 나간 바퀴가 영원히 "진행 중"으로 남아, 그 팀을 다시 시작할 수 없다.

```
data: { runId, status }
```

### `GET /api/solve/runs/{runId}`

바퀴 하나의 상태와 결과. 진행 화면과 결과 화면이 함께 쓴다.

```
data: { runId, departmentId, departmentName, mode, cursor, total, status,
        problems: [...], results: [{ problemId, correct }] }
```

답 제출은 **지금 쓰는 창구를 그대로 쓴다.** 채점과 풀이 이력은 이미 거기서 남는다.

## 예외 처리

| 상황 | 동작 |
|---|---|
| 바퀴에 담긴 문제가 그사이 보관 처리됨 | 불러오기가 실패하면 `correct: null` 로 전진해 건너뛴다 — 맞은 것으로도 틀린 것으로도 세지 않는다 |
| 문제 불러오기가 계속 실패 | "여기서 그만두고 결과 보기" — `finish` 로 바퀴를 끝내고, 지금까지 낸 답은 지킨 채 결과 화면으로 나간다 |
| 남의 바퀴 id 로 접근 | 거절한다 |
| 담을 문제가 0개 | 바퀴를 만들지 않고 안내한다 |
| 새로고침 뒤 "다음 문제" 두 번 누름 | `fromCursor` 가 어긋나 두 번째는 아무것도 하지 않는다 |

## 어느 팀을 고를 수 있나

**전 부서다.** 직원은 자기 부서 문제만 보는 것이 아니라 전 부서 문제를 본다 — 이관 시점에 확정된 규칙이고(`lib/db/solveProblems.ts` 의 S9 주석), 랜덤 풀기도 같다. 이번 변경에서 바꾸지 않는다.

## 지울 것

검색을 없애면 다음 두 화면으로 가는 길이 사라진다.

- 문제 목록 화면 (`screens/solve/SolveProblemListPage.jsx`)
- 문제 하나를 푸는 주소와 화면 (`/solve/[id]`, `screens/solve/ProblemSolvePage.jsx`)

**화면과 주소는 지우고, 그 뒤의 목록 조회 API·쿼리·테스트는 남긴다.** 그 쿼리에는 옛 Spring 동작을 그대로 옮겼다는 기록(파리티 테스트 S5-1·S7·S9)이 붙어 있어, 지우면 이관 근거가 함께 사라진다. 나중에 화면을 되살리기도 쉽다.

| 대상 | 방법 |
|---|---|
| 줄 세우기 규칙(번호 없음·번호 겹침 포함) | 순수 함수 단위 테스트 |
| 다음 위치·완료 판정·`fromCursor` 대조 | 순수 함수 단위 테스트 |
| 팀별 문제 수·진행 상태 조회 | 실제 DB 테스트 |
| 최근 오답 모으기(맞혔다 틀렸다 반복한 경우 포함) | 실제 DB 테스트 |
| 복습 바퀴에서 맞힌 문제가 다음 복습 대상에서 빠지는지 | 실제 DB 테스트 |
| 팀 목록의 `wrongCount` 가 복습 뒤 줄어드는지 | 실제 DB 테스트 |
| 바퀴 시작 세 갈래·전진·완료 | 서비스 단위 테스트 |
| 진행 중 바퀴 중복 생성 시도 | 서비스 단위 테스트 |
| 건너뛴 문제(`correct: null`)가 정답률 계산에서 빠지는지 | 서비스 단위 테스트 |
| 중간에 그만둔 바퀴가 `FINISHED` 가 되어 같은 팀을 다시 시작할 수 있는지 | 서비스 단위 테스트 |
| 담을 문제가 0개일 때 바퀴를 만들지 않는지 | 서비스 단위 테스트 |

## 이번에 다루지 않는 것

- 랜덤으로 풀기 — 그대로 둔다
- 내 풀이 이력 — 그대로 둔다
- 관리자 화면과 통계 — 바퀴를 반영하지 않는다
- 팀 안에서 다시 검색·태그로 좁히기 — 없앤 기능이다
