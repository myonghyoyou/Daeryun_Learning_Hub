# 2025 문제은행(기술직) → 엑셀 일괄등록 변환 결과

원본 `2. 2025년도 문제은행(기술직).pdf`(26쪽, 4단 조판, 500문항)와
`3. 2025년도 문제은행 정답(기술직).pdf`(6쪽, 2단 표)를 관리자 화면
**「문제 엑셀 일괄 등록」** 형식으로 변환한 결과물입니다.

행정직 문제은행(`../문제은행_엑셀/`)과 달리 **팀 구분이 없습니다.** 도시가스사업법 한 과목,
1~500번 연속 번호 한 덩어리입니다.

## 산출물

| 파일 | 내용 |
|---|---|
| `문제_기술직.xlsx` | **업로드용 428문항.** 실제 업로드 코드로 돌려 428건 성공·0건 실패 확인 |
| `_미업로드_빈칸_수동입력.xlsx` | 엑셀로 올릴 수 없어 **개별 등록 화면에서 수동 입력**해야 하는 72문항 |
| `_검증로그.txt` | 유형별 건수 + 수동으로 뺀 문항 목록과 사유 |
| `_맞춤법검사.txt` | 맞춤법·띄어쓰기 검사 결과. 자동으로 고친 것과 사람이 봐야 할 것 |

업로드 428 + 수동 72 = **500문항 전부 반영**(누락 없음). 문항번호 1~500이 두 파일에
정확히 한 번씩만 나옵니다.

## 다시 만들려면

```
cd web && pnpm convert:tech-bank
```

`web/scripts/convert-tech-bank.ts` 가 원본 4개(PDF 2 + HWP 2)를 다시 읽어 이 폴더를 통째로
새로 씁니다. **`pdftotext`(poppler)가 PATH 에 있어야** 합니다 — 없으면 안내 문구를 내고 멈춥니다.

## 맞춤법·띄어쓰기는 어떻게 맞췄나

**PDF 는 조판 결과라 표기를 믿을 수 없습니다.** 한 낱말이 줄 끝에서 갈리면 낱말 두 개로
나오는데, 좌표만 봐서는 원래 붙어 있었는지 알 수 없어 이어 붙일 때 공백이 남습니다
("어 느 것인가?", "석유사 업법", "2가 지를").

그래서 **원본 `.hwp` 를 표기의 기준으로 삼습니다.** hwp 에는 조판 이전의 문단 텍스트가
그대로 들어 있습니다. 공백을 모두 지운 문자열을 열쇠로 원본에서 같은 자리를 찾아,
저자가 실제로 친 띄어쓰기를 되살립니다. 즉 **PDF 는 구조(문항 경계·보기 구분)를,
HWP 는 표기를** 맡습니다.

500문항의 모든 문제내용·보기·정답에 적용했고, 결과는 `_맞춤법검사.txt` 에 있습니다.

| 무엇 | 건수 |
|---|--:|
| PDF 조판 때문에 어긋났던 표기를 원본대로 되돌림 | 552칸 |
| 원본에서 줄맞춤 공백으로 갈려 있던 낱말을 도로 붙임 | 156종 · 연 197회 |
| 글자 차례가 어긋나 있던 칸을 원본 차례로 되돌림 | 39칸 |
| 원본에서 자리를 못 찾아 손대지 못함(사람이 볼 것) | 11칸 |
| 오타 후보(사람이 볼 것, **고치지 않음**) | 2건 |

- **줄맞춤 공백**: 저자가 줄을 맞추려고 낱말 중간에 공백을 여러 칸 넣은 자리("관     리에")는
  hwp 에도 그대로 있어 원본을 봐도 답이 없습니다. 그래서 **말뭉치 근거**로 정했습니다 —
  붙인 꼴이 문서 안에서 조각들보다 자주 쓰이면 붙였습니다("통하"+"여" → "통하여",
  "배"+"관" → "배관"). 붙인 자리는 전부 `_맞춤법검사.txt` 에 적어 두었으니 훑어보세요.
- **글자 차례**: 위첨자·아래첨자(H₂O 의 2, LPG 의 L)는 기준선이 달라 PDF 추출에서 딴 줄로
  밀려 나옵니다. 그 결과 "PG를 연료로 하는 보일러 L", "6만 이하 톤", "방산 , … 탑" 처럼
  글자가 자리를 바꿉니다. 글자 구성은 그대로이므로 같은 글자 묶음을 원본에서 찾아
  제 차례로 돌려놓았습니다("LPG를 연료로 하는 보일러", "6만톤 이하", "방산탑,").
- **오타는 고치지 않았습니다.** 법령 용어는 기계가 판단할 수 없습니다. 후보만 올렸고
  그중 `174번 "디음 중" → "다음 중"` 은 원본의 실제 오타로 보입니다.

## 엑셀 컬럼 (1행 헤더 · 2행부터 데이터)

`문제유형 | 문제내용 | 이미지 | 참조지문 | 보기1~5 | 정답 | 해설 | 태그 | 문항번호`

- **문제유형**: `MCQ_SINGLE` 386 · `MCQ_MULTI` 31 · `SHORT_ANSWER` 11
- **정답**: 객관식은 보기 번호(1부터), 복수정답은 콤마 / 단답은 정답 문자열
- **이미지·참조지문·해설** 열은 비어 있습니다
- **태그**: `기술직`
- **문항번호**: 종이 문제은행에 인쇄된 번호 **그대로**(1~500). 행정직 파일과 달리 **이미 채워져
  있으므로 손댈 것이 없습니다.** 정수 숫자 셀로 저장돼 있으니 열 서식을 바꾸지 마세요 —
  서식이 소수점 두 자리로 잡히면 파서가 `5.00` 으로 읽어 `문항 번호는 숫자여야 합니다` 로
  그 행이 실패합니다.

## 업로드 방법

0. **부서 마스터에 `기술직` 을 먼저 만듭니다.** 이름 `기술직`, 코드 `TECH`.
   지금까지 올린 문제는 전부 행정직 12개 팀에 들어가 있고, 기술직은 팀이 따로 없습니다.
   문항번호는 **부서 안에서만** 유일하면 되므로(`uq_problems_department_source_number`),
   전용 부서를 쓰면 종이 번호 1~500을 그대로 쓰면서 행정직 번호와 절대 겹치지 않습니다.
1. 관리자 로그인 → **문제 관리 → 문제 엑셀 일괄 등록**
2. **귀속 부서를 `기술직` 으로 고릅니다** → `문제_기술직.xlsx` 업로드(428행, 상한 500행 이내)
3. 결과가 **성공 428 / 실패 0** 인지 확인
4. `_미업로드_빈칸_수동입력.xlsx` 의 72문항을 개별 등록 화면에서 입력.
   `문항번호` 열의 값을 문항 번호 칸에 **그대로** 넣으세요.

> ### 부서를 잘못 고른 업로드는 되돌릴 수 없습니다
>
> 귀속 부서 선택은 파일을 바꿔도 **이전 값 그대로 남고**, 결과 화면은 성공/실패 건수만
> 보여 줍니다 — 어느 부서에 들어갔는지는 어디에도 나오지 않습니다.
>
> - **보관(archive)해도 번호는 비지 않습니다.** 유일성 제약이 `(부서, 문항번호)` 만 보고
>   상태 조건이 없어서, 보관한 번호를 다시 올리면 여전히 중복으로 실패합니다.
> - **부서 이동은 번호를 다시 매깁니다.** 옮기면 문항번호가 옮겨 간 부서의 마지막 번호 + 1 로
>   바뀌어, 종이 번호와의 대응이 깨집니다.
> - **둘 다 문제 한 건씩만 처리합니다.** 일괄 취소·일괄 이동은 없습니다.
>
> **올리기 전에 화면의 부서가 `기술직` 인지 확인하는 것이 유일한 방어선입니다.**

> **같은 파일을 두 번 올리면** 모든 행이 `문항 번호 N번은 이 부서에 이미 있습니다.` 로
> 실패합니다. 원인이 행마다 뚜렷이 나오므로 안심하고 재시도해도 됩니다.

## 수동 입력 대상 72문항

| 사유 | 건수 |
|---|--:|
| 다중빈칸(FILL_BLANK) — 괄호가 여러 개 | 54 |
| 정답이 여러 항목(콤마) — 빈칸 채우기로 입력 | 4 |
| 보기는 있는데 정답이 서술형 — **원본 확인 필요** (123·490·495) | 3 |
| 원본 대조 불일치 — 보기가 10개라 5칸에 못 담음 (414·424·426) | 3 |
| 다중빈칸인데 괄호 수와 정답 항목 수가 다름 — **원본 대조 필요** (42·73) | 2 |
| 보기가 없는데 정답이 숫자 — 보기 추출 실패로 보임 (425·454) | 2 |
| **원본 대조 불일치 — 보기 내용이 원본과 다름 (361·485·486)** | 3 |
| 정답이 여러 항목을 늘어놓은 긴 문장 (260) | 1 |

빈칸 채우기는 **엑셀 업로드가 코드에서 막혀 있어**(`빈칸 채우기는 엑셀 업로드를 지원하지
않습니다`) 개별 등록 화면의 빈칸채우기로 넣어야 합니다.

단답(`SHORT_ANSWER`)의 정답 열은 **허용 정답 목록**(적어 낸 한 마디가 목록에 있으면 정답)이지
여러 칸이 아닙니다. 그래서 정답이 콤마로 나뉘는 문항은 하나도 단답으로 내리지 않고 전부
빈칸 채우기로 뺐습니다 — 그러지 않으면 채점이 조용히 틀어집니다.

## 검증: 원본을 두 갈래로 읽어 맞춰 본다

PDF 조판만 봐서는 못 잡는 손상이 있습니다. 아래첨자·위첨자는 기준선이 달라 **옆 보기로
넘어가고**(361번의 H₂O 아래첨자 2가 ③에서 ④로), 동그라미 번호가 통째로 빠져 **두 보기가
한 칸에 붙기도** 합니다(485번의 ⑤, 486번의 ④·⑤). 셋 다 정답 번호는 보기 범위 안이라
기존 검사에는 걸리지 않았습니다 — 그냥 두면 **조용히 틀린 보기**가 됩니다.

그래서 변환기는 문항마다 **PDF 경로(좌표 재구성)와 HWP 경로(문단 구조)를 맞춰 보고**,
지문·보기 개수·보기 내용 중 하나라도 어긋나면 업로드에서 빼 수동입력으로 돌립니다.
한쪽이 다른 쪽을 품기만 해서는 통과시키지 않습니다 — 길이까지 비슷해야 같다고 봅니다
(486번은 보기4가 보기5의 첫 줄을 삼켰는데, 품기 검사만으로는 통과해 버립니다).

산출물은 다음을 확인했습니다.

| 검사 | 결과 |
|---|---|
| 문항 커버리지 | 1~500 각 정확히 한 번 (업로드 428 + 수동 72) |
| 정답 500개를 **HWP 정답표 셀 구조**로 다시 뽑아 대조 | 불일치 0건 |
| 지문·보기를 **HWP 문단 구조**로 다시 뽑아 대조 | 불일치 0건 |
| 보기 개수 대조 | 불일치 0건 |
| 지문·보기 잘림(길이 미달) | 0건 |
| 지문+보기가 완전히 같은 중복 문항 | 0건 |
| 실제 업로드 코드로 적재 | 428건 성공 · 0건 실패 |
| **DB 에 들어간 내용**을 다시 원본 HWP 와 대조 | 지문·보기·정답표시·태그 모두 0건 이상 |

## 알려진 한계 (검수 시 참고)

- **원본에서 자리를 못 찾은 11칸**은 표기를 손대지 못했습니다. `_맞춤법검사.txt` 의
  「원본에서 자리를 못 찾아 손대지 못한 칸」에 전부 적어 두었습니다. 대부분 표로 조판된
  보기라 이미 수동입력으로 빠져 있습니다.
- **저자가 넣은 줄맞춤 공백**은 다 없애지 못했습니다. 붙인 꼴이 문서에 없으면 한 칸으로
  두었기 때문에, "및 안전관리에" 처럼 원문 그대로인 자리와 "가스 공급시설" 처럼 한 칸이
  남은 자리가 섞여 있습니다. 뜻·채점에는 영향이 없습니다.
- **표·수식으로 조판된 보기**: 한 줄로 눌려 들어갑니다. 그런 문항은 대부분 수동입력으로
  빠졌지만(425·454·426 등), 남아 있을 수 있으니 검수 때 보기가 유난히 긴 행을 살펴보세요.
- **참조지문 열 미사용**: 지문이 있는 문항은 `문제내용` 안에 함께 들어갑니다.
- **해설 열 비어 있음**: 정답표에 해설이 없어 채우지 않았습니다.

적재 후에는 `pnpm proof:export` 로 교정용 엑셀을 뽑아 기술직 시트를 훑고,
고칠 것이 있으면 `pnpm proof:apply` 로 되돌려 넣으면 됩니다.

*생성 방식: `pdftotext -bbox-layout` 으로 낱말 좌표 추출 → 4단 경계로 단 분리 후 읽는 순서
재구성 → 정답표는 번호 셀의 세로 가운데 정렬을 조건으로 한 DP 로 행 분할 → **원본 .hwp 와
대조해 띄어쓰기·글자 차례 교정** → 유형 판정 → 어긋나는 문항은 전부 수동입력으로 격리.*
